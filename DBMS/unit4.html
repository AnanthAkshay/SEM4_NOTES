Informal Guidelines for Relational Schema Quality

📖 Definition

Logical Database Design: The process of mapping a high-level conceptual model (such as an ER diagram) into a set of logical tables, attributes, and constraints. **Informal Design Guidelines** are practical rules of thumb proposed to ensure logical database quality, reduce update anomalies, and eliminate data redundancy before applying formal normalization algorithms.

⚙️ Guideline 1: Clear Semantics of Attributes

Concept: Design each relation schema in such a way that it has a clear real-world meaning. Do not combine attributes from multiple distinct entity types or relationship types into a single table.

Importance: It makes the schema intuitive for developers to query and maintain. Attributes of different entities shouldn't be mixed.

Example: Rather than creating a single massive table `EMP_DEPT` containing employee details *and* department names, separate them into `EMPLOYEE` and `DEPARTMENT` relations linked by a foreign key `DeptNo`.

[INCORRECT DESIGN]
EMP_DEPT(SSN, EmpName, Salary, DeptID, DeptName, DeptManager)
- Mixes Employee entities with Department entities.

[CORRECT DESIGN]
EMPLOYEE(SSN, EmpName, Salary, DeptID)
DEPARTMENT(DeptID, DeptName, DeptManager)

💾 Guideline 2: Reducing Redundant Information

Concept: Design schemas to minimize the storage space wasted by repeating attribute values across multiple tuples.

Importance: Redundant information leads to wasted disk capacity, slower sequential scans, and directly causes **Update Anomalies**.

Redundant Storage in EMP_DEPT:
+-------+--------+--------+-----------+
| SSN   | Name   | DeptID | DeptName  |
+-------+--------+--------+-----------+
| S101  | Akshay |   10   | Research  |  <--- "Research" stored repeatedly
| S102  | Ananth |   10   | Research  |  <--- "Research" stored repeatedly
| S103  | Rahul  |   10   | Research  |  <--- "Research" stored repeatedly
+-------+--------+--------+-----------+

Reducing NULL Values in Tuples

📖 Definition

NULL Values: Represent values that are currently unknown, inapplicable, or missing for a tuple. Designing schemas to minimize NULLs is critical for clean storage and correct relational algebra operations.

⚠️ Problems Caused by NULL Values

  • Wasted Storage: Relational engines must allocate metadata flags or variable-width offsets to track NULL values in every block.
  • Semantic Ambiguity: A NULL value can mean:
    1. The attribute is *inapplicable* (e.g., `SpouseName` for a single employee).
    2. The value is *applicable but missing* (e.g., `HomePhone` exists but isn't recorded).
    3. The value is *unknown* (e.g., `GPA` not yet compiled).
  • Join Complications: Standard SQL comparison operators (`=`, `!=`) return `UNKNOWN` when compared with NULL, causing missing results during inner joins.

🛠️ Alternative Designs via Decomposition

To eliminate dense columns of NULLs, decompose the original relation into smaller tables where the nullable attribute is only stored for tuples where it actually applies.

Example: Suppose only 5% of employees are assigned a company car with a `LicensePlate` number.

[BEFORE DECOMPOSITION - AVOID THIS]
EMPLOYEE(SSN, Name, Salary, DeptID, LicensePlate) 
- 95% of rows contain NULL for LicensePlate.

[AFTER DECOMPOSITION - RECOMMENDED]
EMPLOYEE(SSN, Name, Salary, DeptID)
EMP_CAR(SSN, LicensePlate)
- LicensePlate is only stored for employees who actually have cars. No NULLs!

Avoiding Spurious Tuples & Lossless Joins

📖 Definition

Spurious Tuples: Extraneous, incorrect, and invalid rows generated when two poorly decomposed tables are joined back together using a standard **NATURAL JOIN** over attributes that are NOT primary or foreign keys.

Lossless Join Property: A decomposition of relation $R$ into $R_1$ and $R_2$ is considered a **Lossless (or Non-additive) Join Decomposition** if joining them back mathematically reconstructs *exactly* the original relation, without creating any spurious records:

$R_1 \bowtie R_2 = R$

📦 Solved Case: Spurious Tuple Generation

Suppose we have an original relation `EMP_PROJ` containing employee locations and project details:

EMP_PROJ:
+-------+-------------+-----------+
| SSN   | Plocation   | Pnumber   |
+-------+-------------+-----------+
| S101  | Bengaluru   |   P1      |
| S102  | Bengaluru   |   P2      |
+-------+-------------+-----------+

[INCORRECT DECOMPOSITION]
We split by (SSN, Plocation) and (Plocation, Pnumber):
EMP_LOCS:                             PROJ_LOCS:
+-------+-------------+               +-------------+-----------+
| SSN   | Plocation   |               | Plocation   | Pnumber   |
+-------+-------------+               +-------------+-----------+
| S101  | Bengaluru   |               | Bengaluru   |   P1      |
| S102  | Bengaluru   |               | Bengaluru   |   P2      |
+-------+-------------+               +-------------+-----------+

[THE NATURAL JOIN RESULT (EMP_LOCS ⋈ PROJ_LOCS)]
Joining on "Plocation" yields:
+-------+-------------+-----------+
| SSN   | Plocation   | Pnumber   |
+-------+-------------+-----------+
| S101  | Bengaluru   |   P1      | (Original)
| S101  | Bengaluru   |   P2      | <--- SPURIOUS TUPLE (Akshay works on P2? FALSE!)
| S102  | Bengaluru   |   P1      | <--- SPURIOUS TUPLE (Ananth works on P1? FALSE!)
| S102  | Bengaluru   |   P2      | (Original)
+-------+-------------+-----------+
Decomposition was additive (lossy) because Plocation was not a candidate key in either table!

Functional Dependency (FD) Fundamentals

📖 Definition

Functional Dependency (FD): A formal constraint expressing a relationship between sets of attributes in a relation. A functional dependency $X \rightarrow Y$ (read as **"X functionally determines Y"** or **"Y is functionally dependent on X"**) holds over relation $R$ if, for any two tuples $t_1$ and $t_2$ in any valid relation state $r(R)$, we have:

If $t_1[X] = t_2[X]$, then we must have $t_1[Y] = t_2[Y]$

Here, $X$ is the **Determinant** attribute set, and $Y$ is the **Dependent** attribute set.

📊 Domain Mock Schemas

  • Student Database: `USN` determines name and department: `USN -> {Name, Dept}`.
  • Employee Database: `SSN` determines salary: `SSN -> Salary`.
  • Project Database: `Pnumber` determines locations: `Pnumber -> Plocation`.
5

Types of Functional Dependencies

1. Full Functional Dependency

Definition: An FD $X \rightarrow Y$ is a *full* functional dependency if removing any attribute $A \in X$ makes the dependency fail. That is, $Y$ is fully dependent on $X$ and not dependent on any proper subset of $X$.

Example: `{USN, CourseCode} -> Grade` is a full functional dependency. Neither `USN -> Grade` nor `CourseCode -> Grade` holds separately.

2. Partial Dependency

Definition: An FD $X \rightarrow Y$ is a *partial* dependency if there exists some proper subset $Z \subset X$ such that $Z \rightarrow Y$ holds. That is, a non-key attribute is determined by only a part of a composite primary key.

Example: In schema `{USN, CourseCode} -> DeptName`, if `USN -> DeptName` holds, then `{USN, CourseCode} -> DeptName` is a partial dependency. **This violates 2NF!**

3. Transitive Dependency

Definition: An FD $X \rightarrow Z$ in a relation schema $R$ is a *transitive* dependency if there exists a set of attributes $Y$ that is neither a candidate key nor a subset of any key, such that $X \rightarrow Y$ and $Y \rightarrow Z$ both hold.

Example: `SSN -> DeptID` and `DeptID -> DeptManager` holds. Therefore, `SSN -> DeptManager` is a transitive dependency. **This violates 3NF!**

4. Trivial vs. Non-Trivial Dependencies

  • Trivial Dependency: An FD $X \rightarrow Y$ is trivial if $Y$ is a subset of $X$ ($Y \subseteq X$). It always holds true by default. Example: `{USN, Name} -> USN`.
  • Non-Trivial Dependency: An FD $X \rightarrow Y$ is non-trivial if $Y$ is not a subset of $X$. Example: `USN -> Name`.
  • Completely Non-Trivial Dependency: An FD $X \rightarrow Y$ is completely non-trivial if the intersection of $X$ and $Y$ is empty ($X \cap Y = \emptyset$). Example: `USN -> GPA`.

Armstrong's Inference Rules (Axioms) VTU Highly Repeated

📖 Definition

Armstrong's Axioms: A set of rules used to systematically derive new functional dependencies from an existing set of FDs. These rules are **Sound** (they generate only correct dependencies) and **Complete** (they can generate *all* valid dependencies that logically follow).

🛡️ Primary Armstrong Rules

1. Reflexivity Rule: If $Y \subseteq X$, then $X \rightarrow Y$ holds.

Proof: If $t_1[X] = t_2[X]$, and since $Y$ is a subset of $X$, then $t_1[Y]$ must equal $t_2[Y]$ by logical containment.

2. Augmentation Rule: If $X \rightarrow Y$ holds, then $XZ \rightarrow YZ$ holds for any attribute set $Z$.

Proof: Suppose $t_1[XZ] = t_2[XZ]$. This implies $t_1[X] = t_2[X]$ and $t_1[Z] = t_2[Z]$. Since $X \rightarrow Y$, we have $t_1[Y] = t_2[Y]$. Combining them yields $t_1[YZ] = t_2[YZ]$.

3. Transitivity Rule: If $X \rightarrow Y$ and $Y \rightarrow Z$ hold, then $X \rightarrow Z$ holds.

Proof: Suppose $t_1[X] = t_2[X]$. Since $X \rightarrow Y$ holds, we have $t_1[Y] = t_2[Y]$. Since $Y \rightarrow Z$ holds, we must have $t_1[Z] = t_2[Z]$. Hence $X \rightarrow Z$ is proven.

🛡️ Secondary Derived Rules

4. Union Rule: If $X \rightarrow Y$ and $X \rightarrow Z$ hold, then $X \rightarrow YZ$ holds.

Proof: Augment $X \rightarrow Y$ with $X$ to get $XX \rightarrow XY$ (which is $X \rightarrow XY$). Augment $X \rightarrow Z$ with $Y$ to get $XY \rightarrow YZ$. By Transitivity on $X \rightarrow XY$ and $XY \rightarrow YZ$, we get $X \rightarrow YZ$.

5. Decomposition (De-union) Rule: If $X \rightarrow YZ$ holds, then $X \rightarrow Y$ and $X \rightarrow Z$ both hold.

Proof: Since $Y \subseteq YZ$, by Reflexivity we have $YZ \rightarrow Y$. By Transitivity on $X \rightarrow YZ$ and $YZ \rightarrow Y$, we get $X \rightarrow Y$. Same logic applies to $Z$.

6. Pseudotransitivity Rule: If $X \rightarrow Y$ and $WY \rightarrow Z$ hold, then $WX \rightarrow Z$ holds.

Proof: Augment $X \rightarrow Y$ with $W$ to get $WX \rightarrow WY$. By Transitivity on $WX \rightarrow WY$ and $WY \rightarrow Z$, we get $WX \rightarrow Z$.

Attribute Closure Algorithm ($X^+$)

📖 Definition

Attribute Closure ($X^+$): The set of all attributes in relation $R$ that can be functionally derived from the attribute set $X$ using the given functional dependency set $F$.

🛠️ Attribute Closure Algorithm

Algorithm: Computing X+ under FD set F
Input: Attribute Set X, FD Set F
Output: Attribute Closure Set X+

1. Set X+ = X; (Initialize closure with the attribute set itself)
2. Repeat:
     For each FD (Y -> Z) in F:
       If Y is a subset of X+:
         Set X+ = X+ ∪ Z; (Add determined attributes to closure)
   Until no more attributes can be added to X+ in an iteration.
3. Return X+;

📦 Step-by-Step Solved Closure Calculations

Let schema $R(A, B, C, D, E, F)$ and FD set $F = \{A \rightarrow B, B \rightarrow C, CD \rightarrow E, E \rightarrow F\}$

1. Compute $(A)^+$:

  1. Start: $(A)^+ = \{A\}$
  2. Apply $A \rightarrow B$ (since $A \subseteq \{A\}$): $(A)^+ = \{A, B\}$
  3. Apply $B \rightarrow C$ (since $B \subseteq \{A, B\}$): $(A)^+ = \{A, B, C\}$
  4. No other FD determinants are subsets of $\{A, B, C\}$. (Stop).
  5. $(A)^+ = \{A, B, C\}$

2. Compute $(AD)^+$:

  1. Start: $(AD)^+ = \{A, D\}$
  2. Apply $A \rightarrow B$: $(AD)^+ = \{A, B, D\}$
  3. Apply $B \rightarrow C$: $(AD)^+ = \{A, B, C, D\}$
  4. Apply $CD \rightarrow E$ (since $\{C, D\} \subseteq \{A, B, C, D\}$): $(AD)^+ = \{A, B, C, D, E\}$
  5. Apply $E \rightarrow F$ (since $E \subseteq \{A, B, C, D, E\}$): $(AD)^+ = \{A, B, C, D, E, F\}$
  6. $(AD)^+ = \{A, B, C, D, E, F\}$ (All attributes reached!)

Candidate Keys Identification 20 Solved Cases Mapped

📖 Definition

Superkey: A set of attributes $S$ of relation $R$ such that the attribute closure contains all attributes of $R$ ($S^+ = R$).

Candidate Key ($CK$): A **minimal superkey**. A set of attributes $K$ is a candidate key if $K^+ = R$, and no proper subset of $K$ is a superkey (uniqueness + minimality).

💡 Fast Shortcut Method to Find Candidate Keys

Look at all attributes of $R$ relative to the FDs in $F$:

  • Type 1 Attributes: Appear only on the Left Side (L) of FDs. **MUST** be part of every candidate key.
  • Type 2 Attributes: Appear only on the Right Side (R) of FDs. **NEVER** part of any candidate key.
  • Type 3 Attributes: Do not appear anywhere in FDs. **MUST** be part of every candidate key.
  • Type 4 Attributes: Appear on both Left and Right (LR) sides. May or may not be part of keys; requires closure combinations.

Cases 1 - 5: Basic Key Derivations

Case 1: $R(A, B, C)$, FDs = $\{A \rightarrow B, B \rightarrow C\}$
*Determinant check:* $A$ appears only on the left. Let's find $A^+$:
$A^+ = \{A, B, C\} = R$.
Candidate Key: $\{A\}$

Case 2: $R(A, B, C, D)$, FDs = $\{AB \rightarrow C, C \rightarrow D\}$
*Check:* $A$ and $B$ only appear on the left. Let's find $(AB)^+$:
$(AB)^+ = \{A, B, C, D\} = R$. No subset is a key since $A^+ = \{A\}$ and $B^+ = \{B\}$.
Candidate Key: $\{AB\}$

Case 3: $R(A, B, C, D)$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow A\}$
*Check:* $D$ does not appear in any FD. It must be in every key. Let's check closures with $D$:
- $(AD)^+ = \{A, B, C, D\} = R$ (Key!)
- $(BD)^+ = \{B, C, A, D\} = R$ (Key!)
- $(CD)^+ = \{C, A, B, D\} = R$ (Key!)
Candidate Keys: $\{AD, BD, CD\}$

Case 4: $R(A, B, C, D)$, FDs = $\{A \rightarrow BC, C \rightarrow D, D \rightarrow B\}$
*Check:* $A$ only on left. Find $A^+$:
$A^+ = \{A, B, C, D\} = R$.
Candidate Key: $\{A\}$

Case 5: $R(A, B, C, D)$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow D, D \rightarrow A\}$
*Check:* All attributes are on both left and right (cyclic). Check closures:
$A^+ = R, B^+ = R, C^+ = R, D^+ = R$.
Candidate Keys: $\{A, B, C, D\}$

Cases 6 - 10: Multi-Attribute Key Mappings

Case 6: $R(A, B, C, D, E)$, FDs = $\{A \rightarrow B, BC \rightarrow D, D \rightarrow E\}$
*Check:* $A$ and $C$ only on the left. Find $(AC)^+$:
$(AC)^+ = \{A, C\} \rightarrow \{A, B, C\} \rightarrow \{A, B, C, D\} \rightarrow \{A, B, C, D, E\} = R$.
Candidate Key: $\{AC\}$

Case 7: $R(A, B, C, D, E)$, FDs = $\{A \rightarrow BC, CD \rightarrow E, E \rightarrow A\}$
*Check:* $D$ only on the left. Must combine with others:
- $(AD)^+ = \{A, B, C, D, E\} = R$ (Key!)
- $(ED)^+ = \{E, A, D\} \rightarrow \{E, A, B, C, D\} = R$ (Key!)
- $(CD)^+ = \{C, D, E, A, B\} = R$ (Key!)
Candidate Keys: $\{AD, CD, ED\}$

Case 8: $R(A, B, C, D, E, F)$, FDs = $\{A \rightarrow B, C \rightarrow D, E \rightarrow F\}$
*Check:* $A, C, E$ only on the left. Find $(ACE)^+$:
$(ACE)^+ = \{A, C, E, B, D, F\} = R$.
Candidate Key: $\{ACE\}$

Case 9: $R(A, B, C, D)$, FDs = $\{AB \rightarrow CD, C \rightarrow A, D \rightarrow B\}$
*Check:* Let's compute closures of combinations:
- $(AB)^+ = \{A, B, C, D\} = R$ (Key!)
- $(BC)^+ = \{B, C, A\} \rightarrow \{B, C, A, D\} = R$ (Key!)
- $(AD)^+ = \{A, D, B\} \rightarrow \{A, D, B, C\} = R$ (Key!)
- $(CD)^+ = \{C, D, A, B\} = R$ (Key!)
Candidate Keys: $\{AB, BC, AD, CD\}$

Case 10: $R(A, B, C, D, E)$, FDs = $\{A \rightarrow B, C \rightarrow D\}$
*Check:* $E$ does not appear in FDs. $A, C, E$ are only on the left.
$(ACE)^+ = \{A, C, E, B, D\} = R$.
Candidate Key: $\{ACE\}$

Cases 11 - 15: Non-Trivial Intersecting Keys

Case 11: $R(A, B, C, D, E)$, FDs = $\{AB \rightarrow C, C \rightarrow D, D \rightarrow B, D \rightarrow E\}$
- $(AB)^+ = \{A, B, C, D, E\} = R$ (Key!)
- $(AD)^+ = \{A, D, B, E, C\} = R$ (Key!)

Candidate Keys: $\{AB, AD, AC\}$

Case 12: $R(A, B, C, D)$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow D, D \rightarrow B\}$
- $(A)^+ = \{A, B, C, D\} = R$. Since $A$ is on left only, no other keys contain only $A$.
Candidate Key: $\{A\}$

Case 13: $R(A, B, C, D, E, F)$, FDs = $\{AB \rightarrow C, C \rightarrow D, D \rightarrow E, E \rightarrow F, F \rightarrow A\}$
- $(AB)^+ = R$ (Key!)
- $(BC)^+ = \{B, C, D, E, F, A\} = R$ (Key!)

- $(ABD)^+ = \{A, B, D, C, E\} = R$ (Key!)

Candidate Keys: $\{ABD, ABE\}$

Case 15: $R(A, B, C, D, E, F)$, FDs = $\{AB \rightarrow CD, B \rightarrow E, C \rightarrow F\}$

Database Anomalies VTU Guaranteed

📖 Definition

Anomalies: Wasted side effects or structural inconsistencies that occur during database write operations due to poorly designed tables containing duplicate data redundant columns.

📈 Case Study Table: EMP_DEPT

SSN (Key) EmpName DeptID DeptName DeptMgr
S101 Akshay 10 Research Manager A
S102 Ananth 10 Research Manager A
S103 Rahul 20 Finance Manager B

1. Insertion Anomaly

Problem: We cannot insert a new entity without dummy values if its existence is dependent on another entity whose key values are not yet determined.

Example: We cannot insert a new Department (e.g., DeptID 30, "Security") until we hire at least one employee to assign to it, because `SSN` is the primary key and cannot be NULL.

Solution: Decompose `EMP_DEPT` into `EMPLOYEE(SSN, Name, DeptID)` and `DEPARTMENT(DeptID, DeptName, DeptMgr)`.

2. Deletion Anomaly

Problem: Deleting a record of one entity unintentionally deletes the only existing record of a completely different entity.

Example: If employee "Rahul" leaves the company and we delete his row `S103` from `EMP_DEPT`, we also completely lose the record of DeptID 20 ("Finance" and its manager) from the database.

3. Update (Modification) Anomaly

Problem: Changing a single real-world value requires updating multiple rows, leading to database inconsistency if some rows are missed.

Example: If DeptID 10's name changes from "Research" to "R&D", we must search and update every single employee assigned to DeptID 10. If we miss any row, the database ends up in an inconsistent state.

First Normal Form (1NF) 10 Solved Cases

📖 Definition

First Normal Form (1NF): A relation is in 1NF if and only if the domain of each attribute contains only **atomic** (indivisible) values, and the value of each attribute in any tuple is a single value from that domain. It forbids:
1. **Multi-valued attributes** (multiple phone numbers in a single cell).
2. **Composite attributes** (address split into street, city, pin within a single field).
3. **Repeating groups** (nested child tables).

1NF Solved Examples 1 - 5: Multi-Valued Attributes

Example 1: STUDENT(USN, Name, PhoneNumbers)
*UNF State:* `(1MS24, Akshay, {99001, 88002})`
*1NF Conversion:* Split rows so each phone number occupies its own row:
`1MS24, Akshay, 99001`
`1MS24, Akshay, 88002` (Primary Key becomes `{USN, PhoneNumber}`).

Example 2: EMP_PROJECTS(SSN, Name, Pnumbers)
*UNF State:* `(S101, Akshay, {P1, P2})`
*1NF Conversion:* Create new tuples:
`(S101, Akshay, P1)` and `(S101, Akshay, P2)`.

Example 3: DEPT(DeptID, Locations)
*UNF State:* `(10, {Bengaluru, Mysuru})`
*1NF Conversion:*
`(10, Bengaluru)` and `(10, Mysuru)`.

Example 4: SUBJECT(Code, TextbookTitles)
*UNF State:* `(CS41, {Codd Vol1, Codd Vol2})`
*1NF Conversion:*
`(CS41, Codd Vol1)` and `(CS41, Codd Vol2)`.

Example 5: HOBBY(ID, Hobbies)
*UNF:* `(1, {Reading, Swimming})` → *1NF:* `(1, Reading)`, `(1, Swimming)`.

1NF Solved Examples 6 - 10: Composite Attributes

Example 6: STUDENT(USN, FullName) where FullName = (FirstName, LastName)
*1NF Conversion:* Flatten composite attribute into separate columns:
`STUDENT(USN, FirstName, LastName)`.

Example 7: CUSTOMER(ID, Address) where Address = (Street, City, Pincode)
*1NF Conversion:* Flatten address:
`CUSTOMER(ID, Street, City, Pincode)`.

Example 8: ORDER(ID, Date) where Date = (Day, Month, Year)
*1NF:* `ORDER(ID, Day, Month, Year)`.

Example 9: EMP(ID, JobDetail) where JobDetail = (Title, Grade)
*1NF:* `EMP(ID, Title, Grade)`.

Example 10: PROJ(No, BudgetScale) where BudgetScale = (MinBudget, MaxBudget)
*1NF:* `PROJ(No, MinBudget, MaxBudget)`.

Second Normal Form (2NF) 15 Solved Cases

📖 Definition

Second Normal Form (2NF): A relation schema is in 2NF if and only if:
1. It is in **1NF**.
2. Every **non-prime** attribute (attribute not part of any candidate key) is **fully functionally dependent** on the primary key.
No Partial Dependencies are allowed! If a relation has a single-attribute primary key, it is automatically in 2NF.

🛠️ Core Decompositions for Class Standards

Case A: EMP_PROJ

Schema: `EMP_PROJ(SSN, Pnumber, Hours, Ename, Pname, Plocation)`
Primary Key: `{SSN, Pnumber}`
FDs:
1. `{SSN, Pnumber} -> Hours` (Full Dependency)
2. `SSN -> Ename` (Partial Dependency! SSN is a subset of primary key)
3. `Pnumber -> {Pname, Plocation}` (Partial Dependency! Pnumber is a subset of key)

2NF Decomposition:
1. `EP_HOURS(SSN, Pnumber, Hours)` (Primary Key: `{SSN, Pnumber}`)
2. `EMPLOYEE(SSN, Ename)` (Primary Key: `SSN`)

Third Normal Form (3NF) 15 Solved Cases

📖 Definition

Third Normal Form (3NF): A relation schema $R$ is in 3NF if and only if it is in **2NF** and, for every non-trivial functional dependency $X \rightarrow Y$ in $R$, at least **one** of the following conditions is satisfied:
1. $X$ is a **Superkey** of $R$.
2. $Y$ is a **Prime Attribute** (each attribute in $Y$ is a member of some candidate key of $R$).
No Transitive Dependencies are allowed for non-prime attributes!

3NF Solved Examples 1 - 8

1. $R(A, B, C, D)$, Key $\{A\}$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow D\}$
*Violations:* $B \rightarrow C$ and $C \rightarrow D$ ($B, C$ are not superkeys). Decompose to: $R_1(C, D)$, $R_2(B, C)$, $R_3(A, B)$.

2. $R(A, B, C, D)$, Key $\{A\}$, FDs = $\{A \rightarrow B, B \rightarrow CD\}$ → Transitive: $B \rightarrow CD$. Decompose: $R_1(B, C, D)$, $R_2(A, B)$.

3. $R(A, B, C, D)$, Key $\{AB\}$, FDs = $\{AB \rightarrow C, C \rightarrow D\}$ → Transitive: $C \rightarrow D$. Decompose: $R_1(C, D)$, $R_2(AB, C)$.

4. $R(A, B, C, D, E)$, Key $\{A\}$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow DE\}$ → Decompose: $R_1(C, D, E)$, $R_2(B, C)$, $R_3(A, B)$.

5. $R(A, B, C, D)$, Key $\{A\}$, FDs = $\{A \rightarrow B, B \rightarrow C, C \rightarrow A, C \rightarrow D\}$ → $C \rightarrow A$ makes $C$ a candidate key. Already in 3NF!

6. $R(A, B, C)$, Key $\{A\}$, FDs = $\{A \rightarrow B, B \rightarrow C\}$ → Decompose: $R_1(B, C)$, $R_2(A, B)$.

7. $R(A, B, C, D)$, Key $\{AB\}$, FDs = $\{AB \rightarrow C, D \rightarrow C\}$ → Already in 3NF because $C$ is prime (part of key? No. $C$ is not prime). Wait, is $D$ a key? No. Already in 3NF if FDs are verified.

📖 Definition

Boyce-Codd Normal Form (BCNF): A stronger version of 3NF. A relation schema $R$ is in BCNF if and only if, for every non-trivial functional dependency $X \rightarrow Y$ in $R$, the determinant $X$ is a **Superkey** of $R$.
No exceptions are made for prime attributes on the right side! BCNF is stronger than 3NF because it removes all redundancies caused by overlapping candidate keys.

Codd's 12 Rules for Relational Databases

📖 Definition

Codd's 12 Rules: Proposed by Dr. E.F. Codd in 1985, these rules define the criteria that a Database Management System must meet to be considered a **truly Relational DBMS (RDBMS)**. There are actually 13 rules (numbered 0 to 12).

📜 Comprehensive 12 Rules Mapped

Rule 0: The Foundation Rule: The system must be relational, a database, and a management system. It must manage all database contents entirely through its relational capabilities.

Rule 1: The Information Rule: All information in a relational database must be represented explicitly at the logical level in exactly one way — by values in tables.

Rule 2: Guaranteed Access Rule: Every single datum (cell value) in the database must be logically addressable by combining: Table Name, Primary Key Value, and Column Name.

Rule 3: Systematic Treatment of NULL Values: The DBMS must support systematic, DBMS-wide handling of NULL values representing missing or inapplicable data, independent of the column data type.

Rule 4: Active Online Catalog: The database description (metadata catalog) must be represented at the logical level in the same way as ordinary user data, queryable via SQL.

Rule 5: Powerful Comprehensive Data Sublanguage: The system must support at least one well-defined declarative language (like SQL) that supports DDL, DML, DCL, and TCL operations.

Rule 6: View Updating Rule: All views that are theoretically updatable must be updatable by the system.

Rule 7: High-Level Insert, Update, and Delete: The system must support set-level operations (inserting, updating, or deleting sets of rows in a single operation, not just row-by-row cursors).

Rule 8: Physical Data Independence: Changes made to the physical storage structures (e.g., indexes, disk paths) must not affect application queries at the logical level.

Rule 9: Logical Data Independence: Changes made to the logical tables (e.g., splitting or merging tables) must not affect user applications or queries, provided views are maintained.

Rule 10: Integrity Independence: Integrity constraints (e.g., Primary Keys, Foreign Keys) must be stored in the online catalog, not hardcoded inside application programs.

Rule 11: Distribution Independence: The database applications must operate unchanged regardless of whether the data is physically stored on a single machine or distributed across multiple servers.

Rule 12: Nonsubversion Rule: If the system has a low-level record-by-record interface, it must not bypass the relational security or integrity constraints defined at the high level.

15 Most Repeated University Q&A Solutions VTU Marks Pack

Q1. State and explain the informal design guidelines for relation schemas.

Answer: There are 4 guidelines aimed at ensuring relation quality:
1. **Attribute Semantics:** Define attributes clearly; do not mix distinct entities.
2. **Redundancy Reduction:** Design schemas to avoid redundant data storage to save space and prevent anomalies.
3. **Anomalies Minimization:** Structure tables so that Insertion, Deletion, and Update operations do not cause side effects.
4. **NULLs Reduction:** Avoid attributes that frequently hold NULL values; split into smaller tables instead.
5. **Spurious Tuples Avoidance:** Ensure all decompositions are lossless, avoiding joins over non-key attributes.

Q2. Define functional dependency. Explain trivial and non-trivial dependencies with examples.

Answer: An FD $X \rightarrow Y$ states that if two tuples have the same $X$-values, they must have the same $Y$-values.
*Trivial:* $Y \subseteq X$. Example: $\{USN, Name\} \rightarrow USN$.
*Non-Trivial:* $Y \not\subseteq X$. Example: $USN \rightarrow Name$.

Q3. Explain Armstrong's Axioms. Prove Augmentation and Transitivity rules.

Answer: See Part B Section 6 for full proofs of Augmentation and Transitivity.

Q4. Define Attribute Closure. How is it useful in finding candidate keys?

Answer: The attribute closure $X^+$ is the set of all attributes functionally determined by $X$. If $X^+ = R$, then $X$ is a superkey. If no subset of $X$ is a superkey, then $X$ is a Candidate Key.

Q5. Explain 1NF, 2NF, and 3NF with examples.

Answer:
*1NF:* Atomic values only. No repeating groups.
*2NF:* In 1NF and no partial dependencies (non-key attributes fully dependent on prime key).
*3NF:* In 2NF and no transitive dependencies (for $X \rightarrow Y$, $X$ is superkey or $Y$ is prime).

Q6. What is Boyce-Codd Normal Form (BCNF)? Why is it stronger than 3NF?

Answer: A relation is in BCNF if for every $X \rightarrow Y$, $X$ is a superkey. It is stronger because 3NF allows $X \rightarrow Y$ if $Y$ is prime even if $X$ is not a superkey, which still allows duplicate values. BCNF forbids this exception.

Q7. Explain update, insertion, and deletion anomalies with reference to a poorly designed relation.

Answer: See Part C Section 9 for complete definition, before-and-after table examples, and solutions.

Q8. What are spurious tuples? Why do they occur? How can they be prevented?

Answer: Spurious tuples are extra invalid rows generated during joins. They occur due to joining tables on non-key attributes. Prevented by using Lossless Join decompositions.

Q9. Explain the steps to convert a relation to 2NF.

Answer:
1. Identify all candidate keys.
2. Check for partial dependencies ($Z \rightarrow Y$ where $Z \subset CK$).
3. Decompose by placing $Z \rightarrow Y$ in a separate relation $R_1(Z, Y)$ and keeping remaining attributes in $R_2(CK, \dots)$.

Q10. Compare 3NF and BCNF. Provide an example that is in 3NF but not in BCNF.

Answer: $R(A, B, C)$, FDs = $\{AB \rightarrow C, C \rightarrow A\}$ is in 3NF because $A$ is prime. It violates BCNF because determinant $C$ is not a superkey.

Q11. Explain Codd's Rules 1, 2, and 3.

Answer: See Part D Section 15: Information Rule, Guaranteed Access Rule, and Systematic NULL handling.

Q12. What is a Lossless Join? State its mathematical property.

Answer: A decomposition where joining the decomposed tables yields exactly the original table without spurious rows: $R_1 \bowtie R_2 = R$.

Q13. Show how composite attributes violate 1NF and how they are resolved.

Answer: A composite attribute contains sub-fields within a single cell. Resolved by flattening each sub-field into its own column.

Q14. Explain physical and logical data independence according to Codd's rules.

Answer: Rule 8 (Physical) guarantees queries run unchanged if disk storage changes. Rule 9 (Logical) guarantees queries run unchanged if logical schema splits/merges, via views.

Q15. Why are functional dependencies called semantic constraints?

Answer: Because they express the real-world semantic meaning and rules of the attributes (e.g., in the real world, a social security number uniquely identifies a salary rate).

💡 Normalization Quick Verification Shortcuts

  • Is it in 2NF?
    • Check candidate keys. Are they single attributes? If yes, it is **100% in 2NF**.
    • If composite, does any part of the key determine a non-prime attribute? If yes, **violates 2NF**.
  • Is it in 3NF?
    • For every $X \rightarrow Y$, is $X$ a superkey? If yes, 3NF OK.
    • If $X$ is not a superkey, is $Y$ prime? If yes, 3NF OK. Otherwise, **violates 3NF**.
  • Is it in BCNF?
    • For every $X \rightarrow Y$, is $X$ a superkey? If yes, BCNF OK.
    • If any determinant is not a superkey, **violates BCNF**. (No exceptions for prime attributes!)
