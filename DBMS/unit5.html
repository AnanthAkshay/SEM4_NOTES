Single-User vs. Multi-User Transactions

📖 Definitions

Transaction: A logical unit of database processing that includes one or more database access operations (read, write, delete, etc.). It acts as a cohesive execution boundary representing a real-world event (e.g., bank transfer).

Single-User System: A database system where at most one user can execute transactions at any given millisecond. No concurrent operations occur.

Multi-User System: A database system supporting dozens or thousands of concurrent users executing transactions simultaneously on shared disk spaces, necessitating **Concurrency Control** protocols.

📊 Comparison Matrix

Parameter Single-User Database Multi-User Database
Concurrency Zero. Serial queue only. Extremely high concurrent threads.
CPU Utilization Low. CPU is idle during disk I/O. Excellent. Interleaves transactions.
Problems Faced None. Simple database crashes only. Lost updates, dirty reads, deadlocks.
Complexity Very Low. Simple restore systems. High lock managers and schedulers needed.

Read & Write Operations (Primitives)

⚙️ The Database Storage Buffer Model

To understand read/write primitives, we must conceptualize the division between memory buffer pools and physical disk blocks:

 +------------------+                +-------------------------+
 | DATABASE DISK    |                | SYSTEM BUFFER POOL (RAM)|
 |                  |  read_item(X)  |                         |
 | [ Block containing ] ------------▶| [ Buffer copy of X ]    |
 | [ item X on Disk   ]              |                         |
 +------------------+                +-------------------------+
          ▲                                       │
          │ write_item(X)                         │
          │ (Flushes changes                      ▼
          │  back to disk)          [ Local Program Variable x ]

1. Read_item(X) Primitive Mechanics

Syntax: `read_item(X)`

Working Steps:

  1. Find the address of the physical disk block containing item $X$.
  2. Copy that disk block into a system memory buffer (if it's not already in RAM).
  3. Assign the value of item $X$ from the buffer copy to the program local variable $x$.

2. Write_item(X) Primitive Mechanics

Syntax: `write_item(X)`

Working Steps:

  1. Find the address of the physical disk block containing item $X$.
  2. Copy that disk block into system memory buffer (if not in RAM).
  3. Copy the value of the program local variable $x$ into its correct position inside the memory buffer.
  4. Store (flush) the updated buffer block back to physical disk (either immediately or deferred by the buffer manager).

+-----------+       +------------+

📝 Detailed States Breakdown

  • 1. Active: The initial state. The transaction enters this state when it begins execution and remains here while executing its read/write operations.
  • 2. Partially Committed: Enters this state after the final read/write statement has been successfully executed, but before write logs are permanently flushed to disk.
  • 3. Committed: Enters this state after all database changes and transaction log records have been successfully and permanently written to disk. The transaction completes successfully.
  • 4. Failed: Enters this state when the system detects that normal execution can no longer proceed (due to hardware failure, deadlock, or syntax error).
  • 5. Aborted: Enters this state after all side effects of the failed transaction have been cleaned up and the database is rolled back to its original state (via UNDO logs).
  • 6. Terminated: The final end state. The transaction has completely left the system, freeing active buffer pool allocations.

Desirable Properties of Transactions (ACID)

1. Atomicity ("All or Nothing")

Definition: A transaction is an indivisible unit of work. Either all of its database operations are executed successfully, or none are. No partial state is allowed to persist in the database.

Example: Transferring ₹10,000 from Account $A$ to Account $B$. If the system crashes *after* deducting ₹10,000 from $A$ but *before* adding it to $B$, the system rolls back the deduction. Either both are adjusted, or neither.

Implementation: Managed by the database **Recovery Manager** using transaction logs.

2. Consistency Preservation

Definition: A transaction must transform the database from one valid state satisfying all integrity constraints to another valid state. It must not violate schema constraints.

Example: In a double-entry banking book, the sum of balances in $A$ and $B$ must remain unchanged before and after the transfer ($A + B = \text{Constant}$).

Implementation: Shared responsibility between **Database Developers** (correct logic) and **DBMS Constraint Managers** (declaring rules).

3. Isolation

Definition: Even though multiple transactions execute concurrently, they must appear as if they are executing in isolation from one another. The intermediate states of an active transaction must be completely hidden from other concurrent transactions.

Example: While the money transfer is mid-execution, a third auditing transaction must not read $A$'s balance as deducted and $B$'s balance as un-added.

Implementation: Managed by the **Concurrency Control Subsystem** using locks or timestamps.

4. Durability (Permanence)

Definition: Once a transaction commits, its updates to the database must remain permanent and survive any subsequent system crashes or power losses.

Example: If a student's grade update commits, and the college database server crashes a millisecond later, the grade must still exist upon server reboot.

Implementation: Managed by the **Recovery Subsystem** using Write-Ahead Logging (WAL) and disk flushes.

Part B — Concurrency Control & Locking Protocols
6

Need for Concurrency Control (Execution Failures)

📖 Definition

Concurrency Control: The process of managing simultaneous database operations so they do not conflict, preventing database corruption and ensuring transaction isolation.

1. The Lost Update Problem

Problem: Occurs when two transactions read the same initial value, update it, and write it back. One transaction overwrites the committed update of the other, losing the first update forever.

 Lost Update Trace:
+------+-----------------------------+-----------------------------+---------+
| Time | Transaction T1              | Transaction T2              | Value X |
+------+-----------------------------+-----------------------------+---------+
| t1   | read_item(X)                |                             |   80    |
| t2   |                             | read_item(X)                |   80    |
| t3   | x = x - 10                  |                             |   80    |
| t4   |                             | x = x + 20                  |   80    |
| t5   | write_item(X) [writes 70]   |                             |   70    |
| t6   |                             | write_item(X) [writes 100]  |   100   |
+------+-----------------------------+-----------------------------+---------+
T1's deduction of 10 is completely lost! Expected final X = 90, actual = 100.

2. The Temporary Update (Dirty Read) Problem

Problem: Occurs when transaction $T_1$ updates a value, and transaction $T_2$ reads that updated value *before* $T_1$ commits. If $T_1$ subsequently fails and aborts, $T_2$ has read a "dirty" (invalid) state that technically never existed.

 Dirty Read Trace:
+------+-----------------------------+-----------------------------+---------+
| Time | Transaction T1              | Transaction T2              | Value X |
+------+-----------------------------+-----------------------------+---------+
| t1   | read_item(X)                |                             |   80    |
| t2   | x = x - 10                  |                             |   80    |
| t3   | write_item(X) [writes 70]   |                             |   70    |
| t4   |                             | read_item(X) [reads 70]     |   70    |
| t5   | (System Crash / Rollback!)  |                             |   80    |
+------+-----------------------------+-----------------------------+---------+
T2 read X = 70, which was rolled back to 80. T2 read dirty data!

3. The Incorrect Summary Problem

Problem: Occurs when one transaction calculates an aggregate function (e.g., SUM) over multiple rows while another transaction is updating some of those rows. The summary reads some values before the update and others after.

Locking Techniques (Binary & Shared/Exclusive)

📖 Definition

Lock: A mathematical variable associated with a database item that represents the status of that item with respect to possible operations that can be applied to it.

1. Binary Locks

Rules: A binary lock can have only two states: locked (1) or unlocked (0). If an item is locked, no other transaction can access it. Very simple but highly restrictive; prevents concurrent reads.

2. Shared vs. Exclusive Locks (Read/Write Locks)

To maximize concurrency, databases support multiple lock modes:

  • Shared (Read) Lock - `read_lock(X)` or `lock-S(X)`: Multiple transactions can hold shared locks on the same item concurrently to read its value. No writes are allowed.
  • Exclusive (Write) Lock - `write_lock(X)` or `lock-X(X)`: Only one transaction can hold an exclusive lock on an item. It allows both read and write operations. No other transaction can hold any lock on that item.

📊 Lock Compatibility Matrix

Lock Requested Shared (S) Lock Active Exclusive (X) Lock Active Unlocked
Shared (S) Granted (Compatible) Denied (Wait) Granted
Exclusive (X) Denied (Wait) Denied (Wait) Granted

Two-Phase Locking (2PL) Protocol VTU Repeated

📖 Definition

Two-Phase Locking (2PL): A protocol ensuring that all concurrent transaction schedules are **Conflict-Serializable** (correct execution logic). It enforces a rule that a transaction cannot acquire *any* new lock after it has released its first lock.

📈 Two-Phase Lock Transitions

 Locks Held
    ▲
    │         GROWING PHASE                 SHRINKING PHASE
    │      (Lock Acquisition)               (Lock Release)
    │             /\
    │            /  \
    │           /    \
    │          /      \
    │         /        \
    │        /          \
    │       /            \
  ──┴──────/──────────────\─────────────────────────────────▶ Time
        Transaction       Lock point
          Starts      (Max locks acquired)

⚙️ The Two Phases Breakdown

  • 1. Growing Phase: Enters this phase when it starts. The transaction may acquire new locks of any type but is **strictly forbidden** from releasing any locks.
  • 2. Shrinking Phase: Enters this phase the moment the first lock is released. The transaction may release existing locks but is **strictly forbidden** from acquiring any new locks.

📊 Comparison of 2PL Variations

2PL Type Lock Acquisition Rule Lock Release Rule Deadlock Status Cascading Rollback?
Basic 2PL Acquires on the fly. Releases anytime during shrinking. Possible Possible (not strict)
Conservative 2PL Acquires *all* needed locks at start. Releases anytime. Deadlock-Free Possible
Strict 2PL Acquires on the fly. Holds Exclusive (X) locks until COMMIT/ABORT. Possible Prevented
Rigorous 2PL Acquires on the fly. Holds ALL locks (S and X) until COMMIT/ABORT. Possible Prevented

Deadlocks management

📖 Definition

Deadlock: A state where two or more transactions are in a circular wait condition, each waiting for a lock held by the other, halting system execution indefinitely.

🛠️ Deadlock Prevention Schemes (Timestamp-Based)

Suppose transaction $T_i$ requests a lock held by $T_j$. The system compares their timestamps ($TS$):

  • Wait-Die Scheme (Non-preemptive): If $T_i$ is older ($TS(T_i) < TS(T_j)$), $T_i$ is allowed to **wait**. If $T_i$ is younger ($TS(T_i) > TS(T_j)$), $T_i$ **dies** (rolls back and restarts).
  • Wound-Wait Scheme (Preemptive): If $T_i$ is older ($TS(T_i) < TS(T_j)$), $T_i$ **wounds** $T_j$ (preempts and forces $T_j$ to roll back). If $T_i$ is younger, $T_i$ is allowed to **wait**.
Part C — Database Recovery Techniques
10

Recovery Concepts & Log Records

📖 Definition

Database Recovery: The process of restoring the database to the most recent consistent state that existed just before a system crash, transaction failure, or media failure.

📜 Standard Recovery Log Format

The Recovery Manager maintains a write-ahead log containing sequential records of all updates:

  • `[start_transaction, T]` - Transaction $T$ has started.
  • `[write_item, T, X, old_val, new_val]` - Transaction $T$ modified item $X$ from `old_val` (for UNDO) to `new_val` (for REDO).
  • `[commit, T]` - Transaction $T$ successfully committed.
  • `[abort, T]` - Transaction $T$ aborted.
11

Deferred Update (No-Undo/Redo Scheme)

⚙️ Operational Working Rules

Under the **Deferred Update Protocol**, write operations are *deferred* and stored in local memory buffers. The physical database is not modified until after the transaction successfully reaches its commit state.

  • No UNDO Required: Since the database is never modified on disk prior to commit, a failed transaction has written zero dirty data to disk. Hence, we **never** need to undo any changes.
  • REDO Required: If the server crashes *after* commit but before all buffer blocks are flushed, committed updates could be lost. Hence, the recovery system must **REDO** all committed updates.

📋 Recovery Trace Example

Log state at reboot:

[start, T1]
[write_item, T1, X, 100, 200]
[commit, T1]
[start, T2]
[write_item, T2, Y, 50, 80]
<--- CRASH at reboot

Deffered Update Execution Strategy:
1. Check log. $T_1$ is **committed** (contains `[commit, T1]`). REDO $T_1$: Set $X = 200$.
2. $T_2$ is **active** (no commit record). Since updates were deferred, no changes were written to disk for $T_2$. No UNDO needed. Ignore $T_2$.

12

Immediate Update (Undo/Redo Scheme)

⚙️ Operational Working Rules

Under the **Immediate Update Protocol**, write operations are written directly to physical disk blocks even *before* the transaction commits. The system must use Write-Ahead Logging (WAL) to flush log records containing the old value prior to modifying the database block.

  • UNDO Required: If a transaction fails or crashes before committing, its dirty uncommitted changes are already on disk. The system must **UNDO** these changes (restore old values).
  • REDO Required: If a committed transaction's changes were not fully flushed from RAM buffer to disk during a crash, we must **REDO** those updates (apply new values).

📋 Recovery Trace Example

Log state at reboot:

[start, T1]
[write_item, T1, X, 100, 200]
[commit, T1]
[start, T2]
[write_item, T2, Y, 50, 80]
<--- CRASH at reboot

Immediate Update Execution Strategy:
1. Scan the log. Find all committed transactions: **REDO list = $\{T_1\}$**.
2. Find all active/uncommitted transactions: **UNDO list = $\{T_2\}$**.
3. **UNDO Phase:** Scan backward and restore $Y = 50$ (undoing $T_2$).
4. **REDO Phase:** Scan forward and write $X = 200$ (redoing $T_1$).

Checkpoint Mechanisms

📖 Definition

Checkpoint: A recovery optimization point. Periodically, the DBMS pauses active transactions, flushes all modified RAM database buffers and log buffers to disk, writes a `[checkpoint]` record in the log, and resumes transactions.

Purpose: It guarantees that all log records prior to the checkpoint correspond to modifications already permanently written to disk. The recovery engine **never** needs to REDO transactions that committed prior to the checkpoint.

📈 Visual Checkpoint Recovery Ranges

  T1  |--- Committed ---| [CHECKPOINT]
  T2  |------ Committed ------------------------> [CRASH] (Redo T2)
  T3                    |--- Active ------------> [CRASH] (Undo T3)
  ─────────────────────────────┼────────────────────┼────────▶ Time
                          Checkpoint              Crash

The ARIES Recovery Protocol

📖 Definition

ARIES (Algorithms for Recovery and Isolation Exploiting Semantics): A highly robust, industrial-strength recovery algorithm based on three core principles:
1. **Write-Ahead Logging (WAL)**.
2. **Repeating History during Redo** (restores system to exact crash state).
3. **Logging Changes during Undo** (prevents infinite rollback loops during recovery crashes).

🛡️ The Three Phases of ARIES

  1. Analysis Phase: Scans the log *forward* from the last checkpoint to identify:
    • All active transactions at the time of crash (which must be undone).
    • All dirty pages in the buffer pool at the time of crash.
  2. Redo Phase: Scans *forward* from the earliest dirty page log record. It "repeats history" by re-executing all logged updates (both committed and aborted) to restore the database to its exact physical state at the millisecond of crash.
  3. Undo Phase: Scans *backward* from the crash point, rolling back all transactions that were active at the time of the crash by applying the old values. It writes **CLRs (Compensation Log Records)** for every undo operation to prevent redundant rollbacks if the recovery system crashes during this phase.
Part D — NoSQL Databases & Distributed Architectures
15

Why NoSQL? Limitations of SQL

⚠️ Limitations of Relational Databases under Big Data Scale

  • Rigid Schemas: Relational tables require a fixed schema. Adding columns dynamically requires schema alterations that can lock massive tables.
  • Horizontal Scaling (Sharding) Difficulties: SQL relies heavily on joins. Distributing tables across multiple machines (horizontal scaling) makes multi-table joins computationally prohibitive.
  • ACID Overhead: Enforcing absolute ACID consistency locks resources across distributed servers, drastically slowing down high-velocity ingestion (big data).

🛡️ CAP Theorem (Consistency, Availability, Partition Tolerance)

Proposed by Eric Brewer, the CAP theorem states that a distributed data system can provide at most **two** of these three guarantees simultaneously:

  • Consistency (C): Every read request across the cluster receives the most recent write or an error.
  • Availability (A): Every non-failing node returns a non-error response (though not guaranteed to be the most recent write).
  • Partition Tolerance (P): The system continues to operate despite arbitrary network message losses or node splits.

Since network partitions are inevitable in physical clusters, distributed databases must choose between **CP** (Consistency and Partition Tolerance, sacrifice availability) or **AP** (Availability and Partition Tolerance, sacrifice strict consistency in favor of *Eventual Consistency*).

16

The 4 Core NoSQL Storage Models

1. Key-Value & 2. Document Databases

Key-Value Stores: Data is stored as an associative array of key-value pairs. The value is a completely opaque blob to the database engine.
*Use Cases:* Session caching, user profiles.
*Examples:* Redis, Riak.
*Advantages:* Extremely fast sub-millisecond lookup times.

Document Databases: Data is stored as documents (JSON, XML, or BSON). Unlike key-value stores, the document structure is transparent to the engine, allowing indexing on nested document attributes.
*Use Cases:* Content management systems, e-commerce product catalogs.
*Examples:* MongoDB, CouchDB.
*Advantages:* Flexible, schema-less, native JSON storage.

3. Column-Family & 4. Graph Databases

Column-Family Stores: Data is stored in columns grouped into family sets, rather than rows. Columns are stored together on disk, allowing highly optimized aggregation query performance.
*Use Cases:* Web analytics, time-series IoT event tracking.
*Examples:* Apache Cassandra, HBase.
*Advantages:* High write speeds, distributed horizontal scaling.

Graph Databases: Data is represented using nodes (entities) and edges (relationships) with key-value properties. It optimizes deep graph traversal queries.
*Use Cases:* Social networks, recommendation engines, fraud detection.
*Examples:* Neo4j, OrientDB.
*Advantages:* Highly performant for complex relation paths.

17 Most Repeated University Q&A Solutions VTU Marks Pack

Q1. Explain ACID properties of transactions with examples.

Answer: Encompasses Atomicity (all or nothing balance transfer), Consistency Preservation (double entry book totals balance), Isolation (concurrency control locks active state), and Durability (WAL logging protects commits). See Part A Section 4 for complete diagrams and implementations.

Q2. Explain the different states of a transaction with transition diagram.

Answer: See Part A Section 3 for the detailed state transition diagram and descriptions.

Q3. Describe problems that occur in concurrent execution with traces.

Answer: Includes Lost Updates, Dirty Reads, and Incorrect Summaries. See Part B Section 6 for full tracing examples.

Q4. Explain two-phase locking (2PL) protocol.

Answer: The Growing phase allows lock acquisition; the Shrinking phase allows lock release. No locks can be acquired during the shrinking phase. Ensures Conflict-Serializability. See Part B Section 8.

Q5. Differentiate between strict 2PL and rigorous 2PL.

Answer: Strict 2PL holds exclusive locks until commit. Rigorous 2PL holds *all* locks (shared and exclusive) until commit, ensuring strict serializability.

Q6. What are the recovery techniques based on deferred updates?

Answer: All database disk updates are deferred until commit. The system maintains redo lists. No undo operations are ever executed. See Part C Section 11.

Q7. Explain immediate update recovery protocol.

Answer: Disk updates are written immediately. Employs WAL. Uses both undo lists (for active transactions) and redo lists (for committed transactions). See Part C Section 12.

Q8. Explain the ARIES recovery algorithm in detail.

Answer: A three-phase recovery algorithm: Analysis (scans forward), Redo (repeats history forward), and Undo (rolls back backward). Writes CLRs. See Part C Section 14.

Q9. Explain the actions taken during a checkpoint.

Answer: Suspends transactions, flushes active log and RAM dirty buffers to disk, writes `[checkpoint]` log record, and resumes transactions.

Q10. What is CAP theorem? Explain its significance.

Answer: Consistency, Availability, Partition Tolerance. A distributed system can guarantee at most two at once. See Part D Section 15.

Q11. Explain characteristics of NoSQL databases.

Answer: Schema-less, horizontally scalable (sharding), distributed, highly available, and flexible. See Part D Section 15.

Q12. Compare key-value stores and document databases.

Answer: Key-value stores store opaque blobs. Document databases store transparent JSON/BSON structures that can be queried and indexed on nested fields.

Q13. Compare SQL and NoSQL databases.

Answer: See comparison table in Part D Section 17.

Q14. Explain BSON data types in MongoDB.

Answer: String, Integer, Double, Boolean, Array, Object, ObjectId, Date, and Null. See Part E Section 18.

Q15. Write MongoDB query commands for CRUD operations.

Answer: `insertOne()`, `insertMany()`, `find()`, `updateOne()`, and `deleteOne()`. See Part E Section 19.

Q16. What is sharding in MongoDB?

Answer: The process of distributing data across multiple physical machines to support horizontal scaling and high storage capacity.

Q17. Explain wound-wait and wait-die deadlock prevention.

Answer: Wound-wait forces younger lock-holders to abort (preemption). Wait-die forces younger lock-requestors to die (aborts self). See Part B Section 9.
