Java Servlets — Introduction

📖 Definition

A Servlet is a Java class that runs on a web server (server-side) and is used to handle HTTP requests and generate dynamic web content (HTML responses). It extends the capabilities of a web server.

🔑 Key Points

  • Servlets are server-side Java programs that run inside a Servlet Container (e.g., Apache Tomcat)
  • They follow the Request-Response model — client sends request, servlet sends response
  • Servlets are part of Java EE (Enterprise Edition)
  • Package: javax.servlet and javax.servlet.http
  • They are platform independent (written in Java)
  • They are faster than CGI because they use threads instead of processes
  • Servlet lifecycle is managed by the Servlet Container

✅ Advantages of Servlets

  1. Performance — Uses threads (lightweight) instead of processes
  2. Portability — Written in Java, runs on any platform
  3. Security — Java's security manager + type safety
  4. Robustness — JVM manages memory, garbage collection
  5. Persistence — Stays in memory, doesn't restart per request
  6. Java API — Access to full Java API (JDBC, Collections, etc.)
  7. Scalability — Can handle multiple requests concurrently

🔄 Request-Response Paradigm

┌──────────┐         HTTP Request          ┌──────────────────┐
│          │  ──────────────────────────▶  │                  │
│  Client  │     (GET/POST + data)         │   Web Server     │
│ (Browser)│                               │  + Servlet       │
│          │  ◀──────────────────────────  │   Container      │
└──────────┘         HTTP Response         └──────────────────┘
                  (HTML page)

Flow:
1. Client (browser) sends HTTP request to web server
2. Web server forwards request to Servlet Container (Tomcat)
3. Container finds the appropriate servlet
4. Servlet processes request (business logic, DB access)
5. Servlet generates dynamic HTML response
6. Container sends response back to client
💡 Exam One-liner

"A Servlet is a server-side Java program that handles client requests and generates dynamic web content, running inside a Servlet Container like Apache Tomcat."

💡 Why Servlets are better than CGI — OS Context-Switching & Process Overhead

Under the Hood Mechanics: When a request hits a CGI script, the operating system must allocate a brand-new **isolated address space (process)**, load the executable, and initialize it. Processes do not share memory; communicating or context-switching between them requires expensive kernel-level operations. If 1,000 concurrent requests arrive, the OS spawns 1,000 separate processes, rapidly exhausting RAM and CPU cycles.

In contrast, when a request hits a Servlet, the container spawns a lightweight **Thread** within the single JVM process. Threads share the same Heap memory space and resources, making thread creation and context-switching orders of magnitude faster and extremely light on memory.

🧵 Servlet Multithreading & Thread Safety Rules

Because the Servlet Container maintains only **a single instance of each Servlet** (singleton lifecycle) to serve all incoming requests, understanding thread safety is highly critical for the exam:

The Stack vs. Heap Thread-Safety Contract
  • 1. Instance Variables (Class Fields) are NOT Thread-Safe: Fields declared at the class level are stored on the **shared Heap** inside the single servlet instance. If multiple request threads modify these fields concurrently, race conditions and data corruption will occur. Rule: Do not store request-specific state in instance fields!
  • 2. Local Variables (Inside Methods) are 100% Thread-Safe: Variables declared inside `doGet()`, `doPost()`, or local helper methods are allocated on each thread's individual **isolated Thread Stack**. No other thread can see or modify these variables.
⚠️ Deprecated: SingleThreadModel Interface

In early Java EE versions, developers could implement the SingleThreadModel tag interface to guarantee that only one thread executed a servlet's service method at a time (either by queuing requests or instantiating a pool of servlet objects). This was **deprecated** because it severely bottle-necked application scalability and did not solve all shared-state session synchronization issues. Thread-safety should always be achieved by writing stateless servlet code or synchronizing specific blocks.

Servlet Life Cycle

⭐ Most Important Topic
📖 Definition

The Servlet Life Cycle defines the entire process from creation to destruction of a servlet. It is managed by the Servlet Container (not the programmer). The lifecycle has 3 main phases controlled by 3 methods: init(), service(), and destroy().

📋 3 Life Cycle Methods

MethodCalledPurpose

⚠️ Key Points to Remember

1. Only ONE instance of a servlet is created (singleton pattern).
2. init() and destroy() are called only once.
3. service() is called for every request — multiple times.
4. The container manages the entire lifecycle, not the programmer.
5. Multiple threads can call service() simultaneously.

Servlet Container (Web Container)

📖 Definition

A Servlet Container (also called Web Container) is a component of a web server that manages the lifecycle of servlets, maps URLs to servlets, and handles request/response communication. Example: Apache Tomcat.

📋 Responsibilities of Servlet Container

  • Lifecycle management — calls init(), service(), destroy()
  • Multithreading — creates threads for concurrent requests
  • Security — manages access control
  • URL mapping — maps URL patterns to servlets (via web.xml)
  • JSP support — compiles JSP into servlets
  • Communication — provides request/response objects

⚙️ Web Container Socket Listening & Worker Thread Pool

Under the hood, the Servlet Container (like Apache Tomcat) acts as a high-performance network server:

  1. Socket Connection: The container runs a network listener loop on a specific TCP port (default: 8080). When a request socket connection is accepted, the container avoids the expensive overhead of creating a new OS thread on-the-fly by leveraging a pre-allocated Worker Thread Pool.
  2. Request Wrapping: An active worker thread is fetched from the pool. It reads the raw HTTP TCP byte stream and parses it, instantiating the typed objects: HttpServletRequest (containing headers, parameters, URI) and HttpServletResponse (holding socket output buffers).
  3. Servlet Lookup & Invocation: The worker thread matches the request URI against the container's URL mapping index. Once matched, it locates the single Servlet instance on the heap and calls its `service(request, response)` method.
  4. Resource Recycle: Once the servlet method completes, the socket response buffer is flushed back to the client, the request/response objects are nullified for garbage collection, and the worker thread is returned to the pool.

🏷️ URL Mapping: web.xml vs. @WebServlet Annotation

Servlet 3.0 introduced annotation-based configurations to eliminate massive XML deployment descriptors. Today, you can configure mapping in two ways:

1. Traditional XML Mapping (web.xml)
<servlet>
  <servlet-name>Demo</servlet-name>
  <servlet-class>com.pkg.DemoServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>Demo</servlet-name>
  <url-pattern>/demo</url-pattern>
</servlet-mapping>
2. Annotation Mapping (@WebServlet)
import javax.servlet.annotation.*;
 
@WebServlet(
    name = "Demo", 
    urlPatterns = {"/demo"},
    initParams = {
        @WebInitParam(name="k", value="v")
    }
)
public class DemoServlet extends HttpServlet {
    ...
}

GenericServlet Class

📖 Definition

GenericServlet is an abstract class in javax.servlet package that implements the Servlet and ServletConfig interfaces. It is protocol-independent — not tied to HTTP. It provides default implementations for all lifecycle methods except service().

📋 Important Methods

MethodDescription
init(ServletConfig config)Called once to initialize the servlet
init()Convenience method (no-arg), override this for custom init
abstract service(ServletRequest, ServletResponse)Must override — handles requests
destroy()Called before servlet is destroyed
getServletConfig()Returns ServletConfig object
getServletContext()Returns ServletContext object
getServletInfo()Returns info string about servlet
getInitParameter(String name)Gets init parameter value
log(String msg)Writes to servlet log

📝 GenericServlet Example

import javax.servlet.*;
import java.io.*;

public class MyGenericServlet extends GenericServlet {

    public void service(ServletRequest req, ServletResponse res)
            throws ServletException, IOException {

        res.setContentType("text/html");
        PrintWriter out = res.getWriter();
        out.println("<h1>Hello from GenericServlet!</h1>");
        out.close();
    }
}
💡 Key Point

You must override service() method in GenericServlet — it is abstract. GenericServlet is rarely used directly; we mostly use HttpServlet for web applications.

Session Tracking in Servlets

MSRIT SEE '24 / '25
📖 Definition

Session Tracking is the mechanism of maintaining the state (conversational state) of a user across multiple requests sent to a web application. Since HTTP is a stateless protocol (each request is treated as a brand new independent transaction), session tracking is mandatory to build shopping carts, user logins, and multi-step forms.

🔑 Why HTTP is Stateless

Under the HTTP protocol, once the server sends a response back to the client browser, the connection is closed, and the server forgets all details about the client. In a multi-page checkout flow, the server wouldn't know that the request for "Page 3 (payment)" is from the same user who added items on "Page 2 (cart)". Session tracking acts as the cohesive link.

⚙️ The Four Core Session Tracking Mechanisms

Java Servlet technology provides four standard approaches to track sessions:

1. Cookies

Cookies are small text-based key-value files sent by the server and stored locally on the client's web browser. For subsequent requests, the browser automatically attaches these cookies, allowing the server to recognize the client.

// Writing a Cookie
Cookie userCookie = new Cookie("username", "Akshay");
userCookie.setMaxAge(24 * 60 * 60); // Expires in 24 hours
response.addCookie(userCookie);

// Reading Cookies
Cookie[] cookies = request.getCookies();
if (cookies != null) {
    for (Cookie c : cookies) {
        if (c.getName().equals("username")) {
            String val = c.getValue();
        }
    }
}

2. HttpSession (Recommended ✅)

An interface that stores user-specific data **on the server heap**. The container automatically creates a unique session identifier called JSESSIONID and sends it to the client browser via a temporary cookie. The client sends this ID back, and Tomcat links it to their server-side session object.

// Accessing/Creating the Session
HttpSession session = request.getSession(); // true by default (creates if absent)

// Storing an attribute
session.setAttribute("cartItems", list);

// Retrieving an attribute
ArrayList items = (ArrayList) session.getAttribute("cartItems");

// Terminating the Session (Logout)
session.invalidate();

3. URL Rewriting

Used as a backup when cookies are disabled on the client browser. The server appends the session identifier (;jsessionid=12345) directly to every internal hyperlink or action URL in the application. When the user clicks the link, the server parses the session ID from the URL.

// Rewriting a URL in HTML anchor tag
String rawUrl = "profile.jsp";
String encodedUrl = response.encodeURL(rawUrl);
out.println("<a href='" + encodedUrl + "'>View Profile</a>");
// Renders as: <a href='profile.jsp;jsessionid=abc123xyz'>View Profile</a>

4. Hidden Form Fields

Stores the session identifier inside an invisible text field of an HTML form. When the form is submitted, the field value is sent along with other POST parameter values. Only works for form-based requests.

<form action="CheckoutServlet" method="POST">
    <input type="hidden" name="sessionID" value="98765" />
    <input type="submit" value="Pay Now" />
</form>

🤝 HttpSession Under the Hood: JSESSIONID Handshake

When you call request.getSession(), the container executes a state management handshake behind the scenes:

  1. Session Creation: The container allocates a new StandardSession object on the server heap and generates a cryptographically secure, random 32-character string known as the Session ID (e.g. JSESSIONID).
  2. Cookie Handshake: The container writes the Session ID to the HTTP response header: Set-Cookie: JSESSIONID=abc123xyz; Path=/; HttpOnly.
  3. Subsequent Requests: For every future request, the client browser reads this cookie and automatically appends it to the request header: Cookie: JSESSIONID=abc123xyz. Tomcat extracts this ID and maps the incoming thread context to the stored Heap session object.
Session State Serialization Requirement
Any user-defined object stored inside the HttpSession (e.g., a custom Cart class) must implement the java.io.Serializable interface. This allows the web server to write session states to disk when saving memory (session passivation) or replicate them across clusters of servers for high availability. If a non-serializable object is placed in a session, the JVM throws a NotSerializableException during server restarts.
⚠️ Session Timeout Boundaries & Lifespans
A session occupies Heap memory on the server. If a user closes their browser without logging out, the session stays alive until a timeout threshold is exceeded. You can configure timeouts in two ways:
  • 1. Globally in web.xml: (Configured in minutes) 
    <session-config>
    <session-timeout>30</session-timeout> <!-- 30 minutes -->
</session-config>
  • 2. Programmatically in Java: (Configured in seconds) 
    session.setMaxInactiveInterval(1800); // 1800 seconds = 30 minutes

To share objects across different parts of a web application, Java EE defines four distinct data scopes with clear boundaries and lifespans:

What is a JSP Page?

📖 Definition

JavaServer Pages (JSP) is a server-side technology used to create dynamic, platform-independent web applications. It allows developers to embed standard Java code and expression tags directly within static HTML content, simplifying the creation of user interfaces.

🚀 Key Advantages of JSP over Servlets

  • No Tedious output writing: Unlike Servlets which require wrapping every single HTML tag inside out.println() statements, JSP allows you to write clean, standard HTML code directly.
  • Separation of Concerns: Web designers can work on the layout (HTML/CSS) while Java programmers build backend logic without stepping on each other's toes.
  • Auto-Compilation & Deployment: If you modify a JSP page, the container automatically detects the change, recompiles it, and redeploys it in the background. Servlets require manual compiling, server restarts, or redeploying.
  • Built-in Implicit Objects: Common objects like request, response, and session are automatically available in JSP without needing instantiation.
⭐ Servlets vs JSP Comparison
Feature Servlet JSP
Nature A Java class that can contain HTML tags inside it. (Java-dominant) An HTML page that can contain Java code blocks inside it. (HTML-dominant)
Target Audience Java backend programmers. Web designers and frontend UI engineers.
Compilation Compiled manually before deployment. Compiled automatically by the container upon the first request.
Separation of Logic Poor — mixing presentation and logic is common. Excellent — clean separation using custom tags and Expression Language (EL).
Performance Slightly faster (pre-compiled). Has a minor delay on the very first request (compilation phase), then runs at identical speeds.

📄 Creating Static Content in JSP

Static content refers to the fixed parts of a JSP page that do not change based on user requests, business logic, or databases. In JSP, creating static content is extremely easy and natural:

  • Plain text and Markup: Any HTML, CSS, JavaScript, plain text, or images written directly in a .jsp file are treated as static content.
  • Behind the Scenes Translation: The JSP container automatically translates all static HTML blocks into implicit out.write() statements inside the generated servlet's _jspService() method.
  • Example: 
    <!DOCTYPE html>
<html>
<head>
    <title>Static Content Demo</title>
</head>
<body>
    <h1>Welcome to My College Portal!</h1>
    <p>This paragraph and heading are 100% static HTML content.</p>
</body>
</html>

⚙️ Creating Dynamic Content in JSP

Dynamic content refers to web content that is generated on-the-fly by the server at runtime. It changes based on the user's action, input, session state, or backend database values. In JSP, dynamic content is created using scripting elements, actions, or Expression Language (EL):

  • Using Scripting Elements: Developers embed Java expressions, statements, and declarations to compute values dynamically.
  • Rendering on the Browser: The calculated dynamic values are sent as character text to the client's browser, which renders it seamlessly.
  • Example: A JSP page that prints the current server date and time along with a dynamic greeting: 
    <!DOCTYPE html>
<html>

    <title>Dynamic Content Demo</title>

    <h2>Dynamic Greeting App</h2>

    <%
        java.util.Date d = new java.util.Date();
        int hour = d.getHours();
        String greeting = "";
        if (hour < 12) greeting = "Good Morning!";
        else if (hour < 16) greeting = "Good Afternoon!";
        else greeting = "Good Evening!";
    %>

The Lifecycle of a JSP Page

⭐ Highly Critical
🔄 Architecture & Execution Phases

JSP pages are translated into standard Java Servlets by the web container before execution. The lifecycle consists of these strict sequential phases:

 [JSP Code] (.jsp)
     │
     ▼ (Phase 1: Translation)
 [Servlet Source Code] (.java)
     │
     ▼ (Phase 2: Compilation)
 [Compiled Bytecode] (.class)
     │
     ▼ (Phase 3: Loading & Instantiation)
 [Servlet Instance on Heap]
     │
     ▼ (Phase 4: Initialization)
 [jspInit() called]
     │
     ▼ (Phase 5: Request Processing)
 [_jspService() called]  ◀── (Repeated for every client request)
     │
     ▼ (Phase 6: Destruction)
 [jspDestroy() called]

📝 Detailed Lifecycle Steps

  1. Translation Phase: The Servlet Container (e.g. Tomcat) parses the JSP file and translates it into standard Java Servlet source code (extending HttpJspBase). Static HTML text is translated into out.write() statements inside the generated service method.
  2. Compilation Phase: The generated .java servlet source file is compiled into a high-performance bytecode .class file by the standard Java compiler.
  3. Loading & Instantiation: The container loads the compiled servlet class into memory and creates an instance of it on the heap.
  4. Initialization (jspInit()): The container calls the jspInit() method once. Developers can override this to perform one-time setups (like initializing database connections or reading configuration details).
  5. Request Service (_jspService()): For every client HTTP request, the container spawns a new thread and calls the _jspService(HttpServletRequest, HttpServletResponse) method. This executes dynamically and generates the output HTML. Note: You cannot override this method directly.
  6. Destruction (jspDestroy()): Called once by the container when the application is shut down or unloaded, allowing resources to be cleanly closed (closing files, releasing database connections).

Scripting in JSP Pages

MSRIT SEE '24
📖 Scripting Elements

Scripting elements permit you to embed custom Java code directly into the HTML body. There are exactly three main scripting elements: Declarations, Scriptlets, and Expressions.

1. JSP Declarations (<%! ... %>)

Used to declare **class-level variables and methods**. These variables are initialized when the JSP page is initialized and are shared globally among all client requests.

  • Translation: Placed **outside** the generated _jspService() method, directly as instance fields and methods in the generated servlet class.
  • Syntax: <%! int count = 0; %> or <%! int square(int n) { return n*n; } %>

2. JSP Scriptlets (<% ... %>)

Used to embed **any block of standard Java statements**. You can write variables, control flow loops (`if`, `for`, `while`), or local calculations inside them.

  • Translation: Copied **directly inside** the _jspService() method body by the translator.
  • Syntax: <% int x = 10; if (x > 5) { out.println("Greater"); } %>

3. JSP Expressions (<%= ... %>)

Used to **evaluate a Java expression and print its value** directly onto the output HTML page. It acts as an inline print block.

  • Translation: Translated into an implicit out.print(...) statement inside the generated _jspService() method.
  • Crucial Rule: Do **not** write a semicolon (`;`) at the end of a JSP expression! It will result in a translation error.
  • Syntax: <%= x %> or <%= "Welcome, " + name %>

🔄 JSP-to-Servlet Compilation Mapping

During the Translation phase, the JSP container parses the .jsp file and generates a full Java class extending HttpJspBase. Here is exactly how each JSP tag maps inside and outside the compiled servlet's class body:

JSP Source Tag (Page.jsp) Translated Java Servlet Code (Page_jsp.java)
1. Directive Tag (<%@ ... %>) 
<%@ page import="java.util.List" %>
 Placed at the top of the file (Imports) 
import java.util.List;
2. Declaration Tag (<%! ... %>) 
<%!
    int visitCount = 0;
    public int getSquare(int x) {
        return x * x;
    }
%>
 Placed as class-level instance fields & methods (Outside _jspService()) 
public class _jsp_page extends HttpJspBase {
    int visitCount = 0;
    public int getSquare(int x) {
        return x * x;
    }
    // ... _jspService() method follows ...
}
3. Scriptlet Tag (<% ... %>) 
<%
    visitCount++;
    String user = request.getParameter("name");
%>
 Placed as statements inside _jspService() method 
public void _jspService(HttpServletRequest request,
                         HttpServletResponse response) {
    // ... local variables ...
    visitCount++;
    String user = request.getParameter("name");
    // ...
}
4. Expression Tag (<%= ... %>) 
<p>Welcome, <%= user %></p>
 Translated to implicit out.print() statements inside _jspService() 
out.write("<p>Welcome, ");
out.print(user);
out.write("</p>\n");
💡 Critical Thread-Safety Note (Declarations vs. Scriptlets)

Because variables declared in a **Declaration Tag** (<%! %>) are translated into instance variables of the servlet class, they are stored on the **Heap** and shared among all users. They are **NOT thread-safe**.

Conversely, variables declared inside a **Scriptlet Tag** (<% %>) are compiled as local variables inside the _jspService() method. They are stored on each thread's private **Stack** and are **100% thread-safe**.

🏷️ JSP Directives Syntax & Types

JSP Directives are instructions sent to the JSP container during the translation phase, guiding how the page should be compiled. Directives do not produce direct output in the response.

  • 1. Page Directive (<%@ page ... %>): Defines page-specific properties such as language, imports, session configuration, error pages, and buffer size. 
    <%@ page language="java" contentType="text/html; charset=UTF-8" import="java.sql.*" isErrorPage="false" %>
  • 2. Include Directive (<%@ include ... %>): Statically merges the content of another raw file (HTML, JSP, text) into the current page during the translation phase (before compilation). 
    <%@ include file="header.jsp" %>
  • 3. Taglib Directive (<%@ taglib ... %>): Declares a custom tag library (such as JSTL) with a custom prefix, allowing the page to use custom XML-like tags instead of raw Java scriptlets. 
    <%@ taglib uri="http://java.sun.com/jsp/jstl/core" prefix="c" %>
⭐ Static Include vs Dynamic Include
Parameter Static Include (<%@ include %>) Dynamic Include (<jsp:include />)
Syntax <%@ include file="filename.jsp" %> <jsp:include page="filename.jsp" />
Phase of Action Translation / Compilation Phase (Design time) Request Runtime Phase (Execution time)
How it Works The container copies the raw source code of the included file directly into the parent file. They are compiled into a **single Servlet class**. The container processes the included page independently, compiles it to a **separate servlet**, and forwards the request dispatcher at runtime to merge the generated HTML output.
Runtime Performance Faster — No runtime request forwarding overhead. Runs as a single contiguous servlet. Slightly slower — Incurs overhead from runtime context-switching and request dispatcher delegation.
Variable & Scope Sharing Shared — The parent page and included page share local variables because they compile into the same method. Isolated — Local variables cannot be shared directly. Communication must happen via Request attributes.
Dynamic Changes If the included file is modified, the change might not be reflected unless the parent JSP is touched or recompiled. Changes to the included file are **instantly updated** and reflected at runtime without touching the parent page.
Use Cases Best for static, unchanging template parts like **global CSS imports, headers, or footers**. Best for **dynamic elements, database-driven sidebars, or interactive content blocks** that require separate processing.

JSP Implicit Objects

MSRIT SEE '25
📖 Definition

JSP Implicit Objects are pre-defined Java objects that are created by the container and automatically made available inside the JSP page. You can use them directly inside scriptlets or expressions without declaring or instantiating them.

📋 The 9 Core Implicit Objects

Implicit Object Class / Interface type Purpose & Description
request javax.servlet.http.HttpServletRequest Accesses incoming client request parameters, headers, cookies, and scopes.
response javax.servlet.http.HttpServletResponse Sends HTTP response attributes, redirects, content types, or cookies to client.
out javax.servlet.jsp.JspWriter An output stream writer used to write dynamic HTML character content to the client browser.
session javax.servlet.http.HttpSession Used to store user-specific state attributes across multiple page visits.
application javax.servlet.ServletContext Used to get initialization parameters and share objects globally across the entire application.
config javax.servlet.ServletConfig Provides initialization parameters specific to this single translated JSP page.
pageContext javax.servlet.jsp.PageContext Represents the execution context. Can get, set, and find attributes in different scopes.
page java.lang.Object A synonym for this. Refers to the translated servlet class instance itself.
exception java.lang.Throwable Only available on JSP pages configured as error pages (i.e. <%@ page isErrorPage="true" %>). Used to inspect error root causes.
Behind the Scenes: Local Initialization in _jspService()

When the JSP container translates a JSP page, it generates a class whose _jspService() method begins by declaring and initializing all 9 implicit objects as local variables. For example:

public void _jspService(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {

    PageContext pageContext = null;
    HttpSession session = null;
    ServletContext application = null;
    ServletConfig config = null;
    JspWriter out = null;
    Object page = this;
    Throwable exception = null; // only if page directive isErrorPage="true"

    try {
        // 1. Retrieve the custom PageContext for this thread's execution
        pageContext = JspFactory.getDefaultFactory().getPageContext(
            this, request, response, "", true, 8192, true);
        
        // 2. Extract references from PageContext to populate all other implicit variables
        application = pageContext.getServletContext();
        config = pageContext.getServletConfig();
        session = pageContext.getSession();
        out = pageContext.getOut();
        
        // 3. JSP dynamic content/scriptlet actions execution start here...
        out.write("<html><body>");
        
    } catch (Throwable t) {
        if (exception == null) {
            // Forward to configured errorPage...
        }
    } finally {
        // 4. Clean up allocations and release thread resources back to factory
        JspFactory.getDefaultFactory().releasePageContext(pageContext);
    }
}

import java.io.*;

    public void init() throws ServletException {

    public void doGet(HttpServletRequest req, HttpServletResponse res)

        out.println("<p>Check server console for lifecycle messages.</p>");

    // Called ONCE — when servlet is being destroyed
    public void destroy() {
        System.out.println("destroy() called — Servlet destroyed");
    }
}

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.*;

public class SessionServlet extends HttpServlet {
    public void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        
        String name = request.getParameter("username");
        
        // 1. Using HttpSession to store username on Server Heap
        HttpSession session = request.getSession();
        session.setAttribute("sessionUser", name);
        
        // 2. Using Cookies to store username on Client Browser
        Cookie userCookie = new Cookie("cookieUser", name);
        userCookie.setMaxAge(30 * 60); // Active for 30 minutes
        response.addCookie(userCookie);
        
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html><body>");
        out.println("<h2>Session and Cookie Initialized!</h2>");
        out.println("<p>Session username: <b>" + name + "</b> (stored on server)</p>");
        out.println("<p>Cookie 'cookieUser': <b>" + name + "</b> (stored on client browser)</p>");
        out.println("<br><a href='WelcomeServlet'>Proceed to WelcomeServlet</a>");
        out.println("</body></html>");
        out.close();
    }
}

📄 WelcomeServlet.java

import javax.servlet.*;
import javax.servlet.http.*;
import java.io.*;

public class WelcomeServlet extends HttpServlet {
    public void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html><body>");
        out.println("<h2>Welcome back! Session Data Retrieval</h2>");
        
        // 1. Reading attribute from HttpSession (does not create a new session)
        HttpSession session = request.getSession(false);
        String sUser = null;
        if (session != null) {
            sUser = (String) session.getAttribute("sessionUser");
        }
        out.println("<p>Retrieved HttpSession Attribute: <b>" + (sUser != null ? sUser : "No session data found!") + "</b></p>");
        
        // 2. Reading value from Cookies
        String cUser = "No cookie found!";
        Cookie[] cookies = request.getCookies();
        if (cookies != null) {
            for (Cookie c : cookies) {
                if (c.getName().equals("cookieUser")) {
                    cUser = c.getValue();
                    break;
                }
            }
        }
        out.println("<p>Retrieved Cookie Value: <b>" + cUser + "</b></p>");
        
        out.println("<br><a href='login.html'>Restart Demo</a>");
        out.println("</body></html>");
        out.close();
    }
}

  11. How to get PrintWriter? → PrintWriter out = response.getWriter();
  12. What is setContentType()? → Sets the MIME type of the response (e.g., "text/html").
  13. Difference between ServletConfig and ServletContext? → Config is per-servlet; Context is per-application.
  14. How many instances of a servlet are created? → Only ONE (singleton).
  15. What is the Delegation Event Model in servlets? → Container delegates request to appropriate servlet based on URL mapping.
  16. Can a servlet handle both GET and POST? → Yes, override both doGet() and doPost().
  17. Why are servlets better than CGI? → Threads vs processes, persistent, platform-independent, more secure.
  18. What happens if you don't map in web.xml? → 404 Not Found error.
  19. Is HttpServlet abstract? → Yes, it's an abstract class.
  20. What is PrintWriter? → A class from java.io used to write text (HTML) to the response output stream.
  21. What is the default HTTP method? → GET (when you type URL in browser).
  22. What exception does a servlet throw? → ServletException and IOException.
  23. What is the Servlet interface? → Root interface that all servlets must implement (directly or indirectly).
  24. What is load-on-startup in web.xml? → Forces servlet initialization at server startup instead of first request.
  25. What port does Tomcat use? → Default: 8080.

2-Mark Important Definitions

TermDefinition (Write exactly this)
ServletA server-side Java program that runs inside a Servlet Container to handle HTTP requests and generate dynamic web content.
Servlet ContainerA component of a web server that manages the lifecycle of servlets, maps URLs, and handles request-response communication. Example: Apache Tomcat.
Servlet APIA set of interfaces and classes in javax.servlet and javax.servlet.http packages that define the contract between servlets and the container.
GenericServletAn abstract class in javax.servlet that implements Servlet interface and provides protocol-independent servlet functionality.
HttpServletAn abstract class in javax.servlet.http that extends GenericServlet and provides HTTP-specific methods like doGet() and doPost().
ServletConfigAn interface that provides configuration information specific to a single servlet, created by the container during initialization.
ServletContextAn interface that provides information about the entire web application, shared among all servlets. Only one per application.
web.xmlDeployment Descriptor — an XML configuration file that maps URL patterns to servlet classes and defines initialization parameters.
PrintWriterA class from java.io package used to write character-based output (HTML text) to the servlet response.
CGICommon Gateway Interface — an older protocol for generating dynamic content by creating a new OS process per request (slower than servlets).
