Classes and Objects (Deep Memory & Lifecycle Mechanics)

📖 Definitions

Class: A logical template, blueprint, or user-defined prototype that encapsulates the variables (states) and methods (behaviors) common to all objects of its type. It is a compile-time concept and occupies no physical memory.

Object: A physical, runtime instance of a class. It has a distinct identity, state, and behavior, and resides directly within the JVM's Heap memory.

📦 Stack vs Heap Memory Allocation

Java divides runtime data storage into two primary segments to manage object references and object data:

Specification Stack Memory (Local & References) Heap Memory (Dynamic Objects)
Data Stored Local variables, primitive values, and 32/64-bit object references (memory addresses). All class instances (actual objects), arrays, and instance variable fields.
Allocation Rule LIFO (Last-In-First-Out) execution. Allocated per method call (thread stack frame). Dynamic allocation at runtime using the new keyword on a global pool.
Lifecycle Automatic cleanup. Memory is reclaimed instantly when the method exits. Reclaimed asynchronously by the Garbage Collector when objects are unreachable.
Scope Visibility Private. Accessible only within the executing thread/method frame. Global. Shared among all threads in the active Java application.

⚡ The new Keyword: Behind the Scenes

When you write Student s = new Student("Akshay");, the JVM executes four consecutive phases:

  1. Memory Allocation: The JVM allocates a contiguous block of memory on the Heap large enough to hold all instance variables of the Student class and its superclasses.
  2. Default Initialization: Instantly initializes all allocated instance fields to their standard defaults (e.g. numeric types to 0/0.0, booleans to false, object references to null).
  3. Constructor Execution: Invokes the targeted constructor, executing constructor chaining (via `super()`) and custom field binding to establish the object's initialized state.
  4. Reference Return: Yields the absolute memory address of the created heap object. The assignment operator (=) binds this reference address to the reference variable s located on the active Stack frame.

♻️ Garbage Collection (GC) Triggers

An object is eligible for garbage collection (GC) when it becomes unreachable—meaning there are zero active stack reference variables pointing to it. GC is triggered in three common scenarios:

  • Reference Reassignment: 
    Student s1 = new Student("Rahul");
s1 = new Student("Priya"); // The first Student object ("Rahul") is now orphaned and eligible for GC
  • Nullification (Explicit Dereferencing): 
    Student s2 = new Student("Ananth");
s2 = null; // The "Ananth" Student object is dereferenced and queued for reclamation
  • Scope Termination: When a local reference goes out of scope (e.g., when a method returns), the stack frame is popped. Any object created inside that method with only local references becomes immediately unreachable.

Constructors & Copy Constructor Mechanics

📖 Definition

A Constructor is a special member block of code invoked implicitly to initialize an object. It shares the identical name of its class, lacks any explicit return type (including void), and is triggered using the new operator.

🧱 Constructor Types & the Copy Constructor Pattern

  • Default Constructor: Injected automatically by the compiler only if zero constructors are defined by the programmer. It takes no arguments and calls the parent no-arg constructor (super()).
  • Parameterized Constructor: Written by the developer to initialize instance variables with custom arguments at the time of creation.
  • Copy Constructor: A parameterized constructor that accepts an object reference of its own class type. Used to create an independent duplicate (deep or shallow copy) of the passed object: 
    class Point {
    int x, y;
    
    Point(int x, int y) { this.x = x; this.y = y; } // Parameterized
    
    Point(Point p) { this.x = p.x; this.y = p.y; }   // Copy Constructor (Cloning)
}

🎯 this Keyword: Namespace Shadowing & Chaining

The this reference variable represents the active object instance. It has three core compiler roles:

  • Resolving Instance Shadowing: When a local parameter shares the identical name as an instance variable, the local parameter "shadows" the instance variable. Prefixing the variable with this. bypasses local scope and targets heap instance memory.
  • Constructor Chaining (this()): Invoking one constructor from another constructor within the same class. This facilitates code reuse. Rule: The call to this() must be the absolute first statement inside the constructor body.
  • Constructor Propagation in Inheritance: In inheritance hierarchies, every subclass constructor must call a parent constructor. If the subclass constructor does not explicitly call super() or this() as its first line, the compiler automatically inserts super(); (no-arg parent constructor call) at compilation time.

Method Overloading & Type Promotion Gaps

📖 Definition

Method Overloading is the defining of multiple methods inside the identical class sharing the same name but with unique parameter signatures (different parameter counts, different types, or different ordering of types). It represents Compile-time (Static) Polymorphism, resolved during compilation.

📈 Automatic Type Promotion in Overloading

If the compiler cannot find a method with an exact parameter type match, it automatically promotes (widens) the passed argument to the next compatible larger type according to this strict hierarchy:

  char ────────▶ int ────▶ long ────▶ float ────▶ double
                 ▲
  byte ──▶ short ┘

If you call a method with a short value and there is no method signature accepting a short, the compiler promotes the argument to int, then long, then float, then double, matching the first available signature.

🚨 Type Promotion Ambiguity Gaps

When multiple overloaded signatures can accept promoted arguments, compile-time ambiguity can occur, leading to a compile error:

class AmbiguityDemo {
    void calculate(int a, double b) { }
    void calculate(double a, int b) { }

    public static void main(String[] args) {
        AmbiguityDemo demo = new AmbiguityDemo();
        // demo.calculate(10, 10); // COMPILE ERROR: reference to calculate is ambiguous
        // Both 10s can be promoted to double in either method, leaving the compiler unable to decide.
    }
}
⚠️ Overloading Signature Rules

Changing the **return type** or **thrown exceptions** of a method alone does not qualify as overloading. The parameter signature **must** differ. If the parameter signature is identical, the compiler flags a *method already defined* duplicate error.

Understanding static, final, & Initializer Blocks

⭐ Modifiers Comparison — static vs final
Specification static Modifier (Class Scope) final Modifier (Immutability)
Variables Shared globally across all object instances. Initialized once when class loads. Becomes a constant. Once assigned, its value is immutable.
Methods Belongs to class. Invoked directly (Class.method()). Cannot access instance members (this/super). Inherited by subclasses, but cannot be overridden.
Blocks Static block initializes static class fields. Runs once when classloader boots. — (N/A)
Classes Used for nested static helper classes. Cannot be inherited (prevents subclassing). E.g. String.

🏗️ Static Blocks vs Instance Initializers

Java supports block-level initializers that execute automatically during class loading and object creation:

  • Static Initializer Block (static { ... }): Runs exactly once when the class is first loaded into memory by the JVM ClassLoader. It executes before the main method starts and before any object is created. Used to initialize complex static parameters.
  • Instance Initializer Block ({ ... }): Runs for every single object instantiation. It executes immediately after the superclass constructor (super()) completes and before the subclass constructor body is executed.

🔒 Compiler Constraints: Blank Finals & Static Blank Finals

Declaring a variable as final requires strict initialization rules governed by the compiler:

1. Instance Blank Final Variables

A final variable declared without an initial value is a "blank final". The compiler demands that a blank final must be assigned a value in every single constructor of the class. Failing to do so triggers a compile error: variable might not have been initialized.

class Transaction {
    final double rate; // Blank Final
    
    Transaction() {
        this.rate = 0.05; // Initialized in Constructor
    }
}

2. Static Blank Final Variables

A static variable declared with the final keyword but no initial value is a "static blank final". Since it belongs to class scope, it cannot be initialized in a constructor. It must be assigned a value inside a static initializer block, otherwise it fails compilation.

class Config {
    static final String appID; // Static Blank Final
    
    static {
        appID = "SYS_PROD_102"; // Initialized inside static block
    }
}

Inheritance & super Keyword (With Diamond Problem Mechanics)

MSRIT SEE '24
📖 Definition

Inheritance: An object-oriented mechanism where a new class (subclass/derived class) inherits the state variables and method definitions of an existing class (superclass/base class). It establishes an IS-A relationship (e.g. Dog IS-A Mammal) using the extends keyword, maximizing code reusability and enabling dynamic polymorphism.

🌟 The super Keyword

The super keyword is an implicit reference variable pointing to the direct superclass instance. It serves three vital roles at the compiler level:

  • To invoke parent constructors: Invoked explicitly as super() or super(arguments). It must be the absolute first statement inside a subclass constructor body.
  • To access parent variables: Disambiguates instance fields when a subclass variable shadows a parent variable of the same name (e.g. super.fieldName).
  • To execute parent methods: Calls overridden method definitions residing in the parent class scope from within the subclass (e.g. super.methodName()).

🗺️ Standard Inheritance Typologies

Java supports three primary class inheritance configurations:

  1. Single Inheritance: A subclass inherits from exactly one superclass (Class B extends Class A).
  2. Multilevel Inheritance: A subclass inherits from a derived class, creating a linear inheritance chain (Class C extends Class B, which extends Class A).
  3. Hierarchical Inheritance: Multiple subclasses inherit directly from a single common superclass (Class B and Class C both extend Class A).

♦️ Multiple Inheritance & The Diamond Problem

Java strictly prohibits multiple class-level inheritance (e.g. class D extends B, C is a compile-time error). This design decision avoids the infamous Diamond Problem:

         [ Class A (fun()) ]
            /          \
           /            \
    [ Class B ]      [ Class C ]  (Both override fun() uniquely)
           \            /
            \          /
         [ Class D (extends B, C) ]
              (Ambiguity! Which fun() does D inherit?)
Why the Compiler Rejects This
If a class D were allowed to extend both B and C, and both parent classes override a method fun() from A, a call to new D().fun() would create a direct structural conflict. The JVM cannot determine which implementation to invoke in the Virtual Method Table (vtable) lookup, causing severe runtime ambiguity. Hence, Java rejects multiple class inheritance to enforce safety and clean compilation.

Method Overriding & Dynamic Method Dispatch (DMD)

MSRIT SEE '25

🔄 Method Overriding Rules & Covariant Returns

Method Overriding represents Runtime (Dynamic) Polymorphism, where a subclass implements its own specialized behavior for an inherited method. Overriding is subject to strict compiler constraints:

  • Identical Signatures: The subclass method name, parameters count, and exact types must be identical to the parent method.
  • Access Modifier Constraints (Visibility Narrowing Rule): Subclass overridden methods **cannot assign a weaker/narrower access privilege** than their parent counterparts. They can only maintain or widen it.
    private (narrowest) ──▶ default ──▶ protected ──▶ public (widest)
    Example: If the parent method is declared protected, the subclass overridden method must be declared protected or public. Declaring it with default or private triggers a compile-time visibility reduction error.
  • Covariant Return Types (Java 5+): While standard overriding requires identical return types, Java allows the subclass method to return a subtype of the type returned by the parent method: 
    class Base { Base get() { return this; } }
class Derived extends Base {
    @Override
    Derived get() { return this; } // Legal Covariant Return (Derived IS-A Base)
}

⚡ Dynamic Method Dispatch (DMD) & Reference Tracing

DMD is the central mechanism by which a call to an overridden method is resolved at **runtime** using late-binding. This allows Java to decouple compile-time specifications from runtime behaviors.

The Golden Rule of DMD
A superclass reference variable can point to any subclass object on the heap. When an overridden method is called, Java determines which version to execute based on the actual Heap Object Type at runtime, NOT the Stack Reference Type declared at compile-time.

Compile-Time vs Runtime Type Tracing:

Parent obj = new Child();
obj.show();
Stage Type Checked Resolution Mechanics
Compile-Time Parent (Reference Type) The compiler checks if the class Parent has declared the method show(). If not, compilation fails instantly (even if Child has it!). Only methods defined in the reference type can be called.
Runtime Child (Heap Object Type) The JVM looks up the actual object on the heap (which is Child) and invokes the subclass's overridden show() method via late-binding.

Abstract Classes (Under the Hood)

📖 Definition

An Abstract Class is a restricted class declared with the abstract keyword that serves as an incomplete template. It **cannot be instantiated** (cannot create objects of it using new), but can declare abstract methods (methods lacking body blocks) that implementing subclasses are forced to define.

⭐ Comparative Analysis: Abstract Class vs Concrete Class
Specification Abstract Class Concrete Class
Instantiation No. Throws compile-time error. Yes. Directly using new Class().
Abstract Methods Allowed. Can contain 0 or more abstract methods. Strictly prohibited. All methods must have a body.
Inheritance Constraint Forceful. Requires a subclass to inherit and implement abstract methods. Optional. Subclassing is allowed but not demanded.
Constructors Yes. Allowed to define constructors for chaining. Yes. Standard constructors.

🏗️ Can Abstract Classes Have Constructors?

Yes, abstract classes **can and do have constructors**. Although they cannot be instantiated directly via new, their constructors are implicitly triggered during subclass object creation through the standard **Constructor Chaining** pipeline:

abstract class Device {
    String brand;
    Device(String brand) { this.brand = brand; } // Abstract class constructor
}
class Phone extends Device {
    Phone(String brand) {
        super(brand); // Triggers Device constructor to initialize heap variables
    }
}

Abstract classes can also fully declare instance fields, static methods, static blocks, and instance initializer blocks to facilitate shared state configuration among all specialized subclasses.

Packages & Access Protection Mechanics

📖 Definition

A Package is a structural namespace container that groups related classes, sub-packages, and interfaces together. It prevents class name collisions (namespace pollution) and manages access security controls across modular boundaries.

📦 Namespace Resolution: import pkg.* vs import pkg.Class

Java supports two mechanisms for bringing external package dependencies into a file's scope:

  • Single-Type Import (import pkg.Class;): Directly imports one targeted class. Resolves any namespace ambiguity instantly if another package shares similar class names.
  • On-Demand (Wildcard) Import (import pkg.*;): Compiles all public classes and interfaces within the package pkg into the compile scope.
    ⚠️ Compile-Time Resolution Rule: Wildcard imports do not import sub-packages (e.g. import java.* does not bring in java.util.*). They are processed strictly at compile-time by the compiler, which translates short names to fully-qualified names in bytecode. Thus, they have zero performance overhead or memory size footprint at runtime.

⚔️ Resolving Package Namespace Clashes

If two distinct packages share a class name (e.g., both java.util.Date and java.sql.Date exist), importing both wildcards triggers a compile clash. To resolve this, you must reference them using their absolute Fully Qualified Class Names (FQCN) in the source code:

// Avoid ambiguous imports in headers, declare absolute paths in bodies
java.util.Date utilDate = new java.util.Date();
java.sql.Date sqlDate = new java.sql.Date(System.currentTimeMillis());

🛡️ The Ultimate Access Protection Matrix

Java's 4 access levels across packaging boundaries are strictly governed by this master layout:

Access Modifier Same Class Same Package Subclass Same Package Non-subclass Different Package Subclass Different Package Non-subclass
private Yes No No No No
default (omitted) Yes Yes Yes No No
protected Yes Yes Yes Yes * No
public Yes Yes Yes Yes Yes

* Compiler Protected Clause: In a different package, a subclass can access protected member fields only through inheritance—meaning inside the subclass body via subclass references or the `super` pointer. It cannot access protected members using an instance reference of the parent class itself inside that different package.

Interfaces (Marker Interfaces & Modern Methods)

📖 Definition

An Interface is a syntactical contract containing abstract specifications. It decouples **what** a class must do from **how** it does it, providing absolute **Loose Coupling** and facilitating **Multiple Inheritance** of behaviors in Java.

🏷️ Marker (Tagging) Interfaces

A Marker Interface is an interface that declares **absolutely zero methods or fields** (empty interface). It serves as a metadata "tag" or capability signal for the JVM, compiler, or libraries.

  • Common Examples: java.io.Serializable, java.lang.Cloneable, java.util.RandomAccess.
  • Execution Mechanism: When a class implements Cloneable, it declares to the runtime that it permits the Object.clone() method to execute a bitwise clone. If a class calls clone() without implementing Cloneable, the JVM intercepts the execution and throws a checked CloneNotSupportedException.

🚀 Modern Interface Evolution (Java 8 & 9 Features)

To prevent interfaces from becoming overly rigid, Java evolved interfaces to support concrete implementations:

Method Type Modifier Syntax Overriding Permission Call Mechanics & Purpose
Default Methods (Java 8+) default Allowed Allows adding new features to interfaces without breaking existing implementing classes (backward compatibility). Invoked on object instances.
Static Methods (Java 8+) static Prohibited Serves as static helper/utility methods. Must be called directly via the Interface name: InterfaceName.staticMethod().
Private Methods (Java 9+) private Prohibited Encapsulates common helper logic shared among multiple default or static methods within the interface itself. Inaccessible to implementing classes.

Concrete Interface Method Implementation Demo:

interface SmartController {
    void operate(); // Abstract contract

    default void initialize() {
        log("Booting controller..."); // Calls private helper
        System.out.println("System Online.");
    }

    static void showVersion() {
        System.out.println("v2.1");
    }

    private void log(String message) {
        System.out.println("[LOG]: " + message); // Encapsulated logic (Java 9)
    }
}

An Exception is an unwanted or abnormal event that halts normal CPU instruction execution at runtime. Exception handling establishes a logical container structure to capture and handle these deviations gracefully, preventing OS-level program crashes.

The Five Keywords & Modern Catch Mechanics

⭐ Critical Exam Topic

🔑 The Core Keywords: try, catch, finally, throw, throws

  • try block: Monitors a scope of statements. Cannot stand alone; must be supported by a minimum of one catch block or a finally block.
  • catch block: The handler routine. Activates ONLY when an exception matching its parameter type is thrown inside the try block. **Rule:** Catch hierarchy must be written from **most specific subclass (e.g. ArithmeticException) to most generic parent class (e.g. Exception)**, otherwise compile errors occur.
  • finally block: Always executes, guaranteed. Runs whether an exception is caught, uncaught, or completely absent. **Purpose:** Closing physical handles (databases, files, stream buffers) to prevent memory leaks.
  • throw: Explicitly triggers an exception object instance: throw new MyException("msg");.
  • throws: Declares possible exceptions in a method signature to shift the handling responsibility up the call stack: void read() throws IOException {}.

⚡ Modern Java 7+ Catch Evolution: Multi-Catch Blocks

To avoid repetitive catch-block code blocks handling similar logic, Java 7 introduced the **Multi-Catch** syntax using the pipe (|) character:

try {
    int res = 10 / Integer.parseInt(args[0]);
} catch (ArithmeticException | NumberFormatException | ArrayIndexOutOfBoundsException e) {
    System.out.println("Invalid parameters supplied: " + e.getMessage());
    // Compiler Rule: The exception variable 'e' in a multi-catch block is implicitly 'final'.
    // Any attempt to reassign 'e' (e.g., e = new ArithmeticException()) results in a compile error.
}
⚠️ Multi-Catch Inheritance Conflict Rule
You **cannot** combine classes in a multi-catch block if they share a direct parent-child relationship (e.g. catch (ArithmeticException | Exception e) is a compile error because ArithmeticException is already caught by Exception).

Try-with-Resources & Custom Exceptions

🛡️ Automatic Resource Management: Try-with-Resources (Java 7+)

Historically, closing resources in a finally block was extremely verbose and vulnerable to resource leaks if the close() method itself threw an exception. Java 7 introduced **Try-with-Resources**, which automatically invokes the close() method on resources declared in the try-header.

The AutoCloseable Contract
To be declared inside a try-with-resources header, the resource class **must implement the java.lang.AutoCloseable** (or its sub-interface java.io.Closeable) contract, which defines the single method: public void close() throws Exception;. 
// The compiler automatically injects a hidden finally block to clean up resources
try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {
    System.out.println(br.readLine());
} catch (IOException e) {
    System.out.println("File read failure: " + e.getMessage());
}

🔥 Suppressed Exceptions Mechanics:

If an exception is thrown inside the try-block (primary exception), and another exception occurs automatically during the resource's close() invocation (secondary exception):

  • The **primary exception is propagated** up the call stack so the programmer handles the primary business error first.
  • The **secondary (close) exception is suppressed** (not discarded!) and attached silently to the primary exception. You can fetch suppressed exceptions using e.getSuppressed().

✍️ Professional Custom Exception Design

To design a custom exception, inherit from Exception (to create a strict checked exception) or RuntimeException (to create a standard unchecked exception):

// Checked Exception (Compiler forced)
class InsufficentBalanceException extends Exception {
    private double deficit;
    
    InsufficentBalanceException(String msg, double deficit) {
        super(msg); // Pass the message to the Exception superclass
        this.deficit = deficit;
    }
    
    public double getDeficit() { return deficit; }
}

🔗 Exception Chaining Architecture

Exception chaining allows wrapping a low-level cause exception inside a high-level logical exception without losing the original stack trace details. Uses `initCause()` or parent Throwable constructors:

try {
    // Low-level JDBC DB Exception
    throw new SQLException("Connection Timeout");
} catch (SQLException dbEx) {
    // Wrap inside high-level business exception
    BankingException bankEx = new BankingException("Transaction Failed");
    bankEx.initCause(dbEx); // Chains dbEx as the root cause
    throw bankEx;
}

5. Multiple Inheritance using Interfaces

6 MARKS

Demonstrates how interfaces resolve the multiple inheritance diamond problem in Java, allowing a class to implement multiple specifications.

interface Printable {
    void print();
}

interface Showable {
    void show();
}

// Class implementing multiple interfaces
class Document implements Printable, Showable {
    @Override
    public void print() {
        System.out.println("Printing Document content... 🖨️");
    }

    @Override
    public void show() {
        System.out.println("Showing Document on Screen... 🖥️");
    }

6. this Keyword & Shadowing Demo

6 MARKS

Demonstrates explicit use of `this` to resolve scope shadowing of instance variables by method/constructor parameters, and invoking current class methods.

class Employee {
    int id;
    String name;
    double salary;

    Employee(int id, String name, double salary) {
        this.id = id;             // 'this.id' is instance variable; 'id' is parameter
        this.name = name;         // 'this.name' is instance variable; 'name' is parameter
        this.salary = salary;
    }

    void display() {
        System.out.println(id + " | " + name + " | $" + salary);
    }

    void promote(double increment) {
        this.salary += increment;
        System.out.print("PROMOTED: ");
        this.display();           // 'this' used to call current instance method
    }
}

public class ThisDemo {
    public static void main(String[] args) {
        Employee emp = new Employee(101, "Ananth", 75000.0);
        emp.display();
        emp.promote(15000.0);
    }
}

Top 10 Viva/Interview Questions
  • Why is the main method static in Java? It allows the JVM to execute the `main` method directly without instantiating the class, saving startup memory and bootstrap overhead.
  • Can we overload the main method? Yes, but the JVM will only execute the standard signature: `public static void main(String[] args)`.
  • What is the difference between abstract classes and interfaces? An abstract class can have constructors, instance fields, non-final variables, and concrete methods. An interface can only have static final constants, default/static methods, and abstract methods, and supports multiple inheritance.
  • What happens if you don't handle a checked exception? The code will fail to compile. The compiler requires you to either catch it using try-catch or declare it in the method signature using the `throws` keyword.
  • Can a catch block exist without a try block? No. A catch block must immediately follow a try block. A finally block is also dependent on the try block.
  • Is `finally` always executed? Yes, except in case of hard VM shutdowns like `System.exit(0)` or extreme hardware power loss.
  • What is the purpose of chained exceptions? It allows developers to propagate a high-level corporate exception while keeping the low-level technical root cause attached for debugging.
  • What is naming clash in packages? When two classes share the same name in different packages. It is resolved by writing fully qualified names (e.g. `java.util.Date` vs `java.sql.Date`).
  • Can an interface implement another interface? No, an interface can only **extend** another interface (multiple extensions are allowed). Classes **implement** interfaces.
  • What is dynamic dispatch used for? It is the mechanism that supports runtime polymorphism, allowing clean interfaces and decoupling subclass behaviors.
