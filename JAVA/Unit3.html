1 Java Collection Framework Overview
Definition
A Collection Framework is a unified architecture for representing and manipulating groups of objects. It provides ready-made classes and interfaces so you don't have to write data structures from scratch.
Why Collections?
  • Arrays have fixed size — Collections are dynamic
  • Collections hold only Objects (reference types)
  • Provides sorting, searching, insertion, deletion
  • All Collection classes are in java.util
Hierarchy (Simplified)
Iterable
  └── Collection
        ├── List  → ArrayList, LinkedList, Vector
        ├── Set   → HashSet, LinkedHashSet, TreeSet
        └── Queue → PriorityQueue, Deque

Map (separate)
  ├── HashMap, LinkedHashMap
  └── TreeMap
List = Ordered + Duplicates allowed. Set = No duplicates. Map = Key-Value pairs.

3 Collection Classes
ArrayList (Dynamic Array Resizing)
  • Backed by a contiguous dynamic array loaded on the Heap.
  • Provides incredibly fast random access in $O(1)$ time via element index bounds.
  • Resizing Overhead: When capacity bounds are exceeded, the JVM reallocates a new array. The scaling formula is: newCapacity = oldCapacity + (oldCapacity >> 1) (which is a 1.5x increase). Old array elements are migrated via Arrays.copyOf().
  • Performance: Inserting or removing elements in the middle requires shifting trailing elements ($O(n)$ time). Not synchronized (thread-unsafe).
ArrayList<String> al = new ArrayList<>();
al.add("Apple"); // Append O(1)
al.add("Banana");
al.add(0, "Mango"); // Insert O(n) due to array shift
al.remove("Banana");
System.out.println(al);
Output
[Mango, Apple]
LinkedList (Node-Link Allocation)
  • Backed by a doubly linked list hierarchy.
  • Node Structure: Allocates separate small objects on the Heap. Each element is wrapped inside a private nested class Node<E> containing pointer references: E item, Node<E> next, and Node<E> prev.
  • No Contiguous Constraints: Eliminates contiguous memory reallocation issues but introduces severe pointer reference memory overhead (24-32 bytes per node).
  • Performance: Faster insertions/deletions at boundary points ($O(1)$). Slow random index access ($O(n)$) because it requires sequential pointer-hopping traversal.
LinkedList<Integer> ll = new LinkedList<>();
ll.add(10);
ll.addFirst(5);   // add at front O(1)
ll.addLast(20);   // add at end O(1)
ll.removeFirst();
System.out.println(ll);
Output
[10, 20]
Storing User-Defined Classes in Collections
⚠️ Critical Requirement: equals() and hashCode()
When storing objects of custom (user-defined) classes in collections, especially hashing-based collections like HashSet or HashMap, you must override the equals() and hashCode() methods. If you don't, Java will use the default implementation from the Object class, which compares object memory addresses, leading to duplicate objects and retrieval failures.

Here is a complete, exam-ready program showing a custom Student class stored in a HashSet, overriding equals() and hashCode() to prevent duplicate entries:

import java.util.*;

class Student {
    String USN;
    String name;

    Student(String USN, String name) {
        this.USN = USN;
        this.name = name;
    }

    // Override hashCode() to compute hash based on unique USN
    @Override
    public int hashCode() {
        return Objects.hash(USN);
    }

    // Override equals() to compare Student objects based on unique USN
    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (obj == null || getClass() != obj.getClass()) return false;
        Student student = (Student) obj;
        return Objects.equals(USN, student.USN);
    }

    @Override
    public String toString() {
        return name + " (" + USN + ")";
    }
}

public class UserDefinedCollectionDemo {
    public static void main(String[] args) {
        Set<Student> set = new HashSet<>();

        Student s1 = new Student("1MS22IS001", "Ananth");
        Student s2 = new Student("1MS22IS002", "Akshay");
        Student s3 = new Student("1MS22IS001", "Ananth Kumar"); // Duplicate USN!

        set.add(s1);
        set.add(s2);
        set.add(s3); // Will be rejected because of duplicate USN

        System.out.println("Students in Set:");
        for (Student s : set) {
            System.out.println(s);
        }
    }
}
Output
Students in Set: Ananth (1MS22IS001) Akshay (1MS22IS002)

Iterator Program — 6 Mark
import java.util.*;
public class IteratorDemo {
    public static void main(String[] args) {
        ArrayList<String> list = new ArrayList<>();
        list.add("Java");
        list.add("Python");
        list.add("C++");
        list.add("Kotlin");

        // Get Iterator
        Iterator<String> it = list.iterator();

        System.out.println("All elements:");
        while (it.hasNext()) {
            String s = it.next();
            System.out.println(s);
        }

        // Remove "Python" using iterator (safe removal)
        Iterator<String> it2 = list.iterator();
        while (it2.hasNext()) {
            if (it2.next().equals("Python"))
                it2.remove();
        }
        System.out.println("After removal: " + list);
    }
}
Output
All elements: Java Python C++ Kotlin After removal: [Java, C++, Kotlin]
✅ Key point: Never use list.remove() inside a for-each loop — it throws ConcurrentModificationException. Always use iterator.remove().
Fail-Fast vs. Fail-Safe Iterators & Structural Verification
Structural Modification & modCount
Java collections use an internal protected field called modCount (inherited from AbstractList / AbstractMap) that keeps track of the number of times the collection has been structurally modified (additions, removals, resizes, clear operations). Changes in elements themselves (like setting a new value using set()) do not affect modCount.

When a Fail-Fast iterator is created, it initializes an internal field expectedModCount = modCount. During iteration, on every call to next() or remove(), the iterator verifies that: 

if (modCount != expectedModCount)
    throw new ConcurrentModificationException();

If any other thread (or the same thread, using a direct collection modification method) modifies the structure, the count mismatch triggers an immediate fail-fast termination to prevent silent data corruption or non-deterministic behaviors.

Fail-Safe (Weakly Consistent) Iterators
Unlike fail-fast, Fail-Safe (more accurately called Weakly Consistent) iterators do not throw ConcurrentModificationException because they operate on a clone/snapshot of the collection's data structure (like CopyOnWriteArrayList) or use lock-free/segment-level structural traversal (like ConcurrentHashMap). They allow modifications during traversal but might not reflect real-time updates made after iterator creation.
Feature Fail-Fast Iterators Fail-Safe (Weakly Consistent) Iterators
Throws Exception? Yes — ConcurrentModificationException if modified. No — safe from concurrent structural exceptions.
Data View Works on the original collection directly. Works on a clone/snapshot or segmented buffer.
Memory Overhead Zero additional memory overhead. High overhead for snapshots (e.g. CopyOnWriteArrayList).
Examples Iterators of ArrayList, HashSet, HashMap, Vector. Iterators of CopyOnWriteArrayList, ConcurrentHashMap.
Modification during loop Must use iterator.remove(); list methods fail. Can use collection's own modification methods safely.
5 Spliterator
Definition
Spliterator (Splittable Iterator) was introduced in Java 8. It can iterate AND split a collection for parallel processing. Designed to work with Streams.
Key Methods
  • tryAdvance(Consumer) — process one element, return false if no more
  • forEachRemaining(Consumer) — process all remaining elements
  • trySplit() — splits into two spliterators for parallel use
  • estimateSize() — estimates remaining elements
Iterator vs Spliterator
  • Iterator: sequential traversal only
  • Spliterator: sequential OR parallel
  • Iterator: for legacy Collections
  • Spliterator: for Java 8 Streams
  • Spliterator can estimate size
import java.util.*;
public class SpliteratorDemo {
    public static void main(String[] args) {
        List<String> list = Arrays.asList("A", "B", "C", "D");
        Spliterator<String> sp = list.spliterator();
        System.out.println("Size: " + sp.estimateSize());
        sp.forEachRemaining(System.out::println);
    }
}
Output
Size: 4 A B C D
6 Working with Maps & Sets
HashSet
  • Implements Set using a hash table
  • No duplicate elements
  • Unordered — no guaranteed order
  • Allows one null value
  • O(1) for add, remove, contains

hs.add("Cat"); hs.add("Dog"); hs.add("Cat");
System.out.println(hs); // [Cat, Dog] — no duplicate
LinkedHashSet
  • Implements Set using hash table + linked list
  • No duplicate elements
  • Ordered — maintains insertion order
  • Allows one null value
  • O(1) performance for operations
LinkedHashSet<String> lhs = new LinkedHashSet<>();
lhs.add("Cat"); lhs.add("Dog"); lhs.add("Cat");
System.out.println(lhs); // [Cat, Dog] — maintains order
TreeSet
  • Implements NavigableSet
  • Elements stored in sorted (ascending) order
  • No duplicates, No null values
  • Backed by TreeMap internally
  • O(log n) for add, remove, contains
TreeSet<Integer> ts = new TreeSet<>();
ts.add(30); ts.add(10); ts.add(20);
System.out.println(ts); // [10, 20, 30]
HashMap
  • Key-value pairs, unordered
  • Keys are unique; values can repeat
  • Allows one null key, multiple null values
  • O(1) average for put/get

hm.put("Alice", 90);
hm.put("Bob", 85);
for (Map.Entry<String,Integer> e : hm.entrySet())

  • Key-value pairs, keys stored in sorted order

HashMap Internals, Hashing Mechanics & Treeification
Step 1: The Supplemental Hash Function & XOR Bit-Shift
When you call put(key, value), HashMap computes a 32-bit integer hash code. To minimize collisions (especially when the hash codes differ only in constant upper bits), it applies a supplemental hashing function using an XOR bit-shift operation: 
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
Shifting the high 16 bits downward and XORing them ensures that high-entropy bits influence the lower index calculation range.
Step 2: Bucket Index Matching via (n - 1) & hash
Rather than using the expensive modulo operator (hash % n), HashMap computes the bucket array index using a bitwise AND operation:
index = (n - 1) & hash
where n represents the current capacity of the internal bucket array (which is always a power of 2, e.g., 16, 32, 64). Bitwise AND on a power of two acts as a high-speed mask.
Step 3: Hash Collisions & Java 8 Treeification Rules
If multiple keys resolve to the same bucket index, they are stored in a linked chain (Singly Linked List of Node<K,V>).
If a chain grows too long, performance degrades from $O(1)$ to $O(n)$. Java 8 introduced an optimization called Treeification:
  • When a bucket's chain length exceeds TREEIFY_THRESHOLD = 8 elements...
  • ...AND the total HashMap capacity is at least MIN_TREEIFY_CAPACITY = 64...
  • The linked list is converted (treeified) into a self-balancing Red-Black Tree of TreeNode<K,V>, reducing lookup times to $O(\log n)$.
  • If the map is resized and elements in a bucket drop below UNTREEIFY_THRESHOLD = 6, the tree is converted back into a standard linked list.
  • Resizing Threshold: When the number of active entries exceeds capacity * loadFactor (where standard loadFactor = 0.75), the array capacity doubles (e.g. 16 to 32) and all elements are rehashed.
Self-Balancing Red-Black Trees in TreeSet & TreeMap

Both TreeSet and TreeMap are backed by an internal Red-Black Tree implementation. Unlike hashing-based structures that offer average $O(1)$ time but rely on complex hashing and array allocations, Red-Black Trees guarantee strict $O(\log n)$ time complexity for fundamental operations (add, remove, contains).

Red-Black Tree Rules enforced on insert/delete:
  1. Every node is either Red or Black.
  2. The root node is always Black.
  3. No two adjacent Red nodes are allowed (Red nodes cannot have Red children).
  4. Every path from a node to any of its descendant NULL nodes must contain the same number of Black nodes (black height equality).
When elements are inserted, the tree preserves balance via left rotations, right rotations, and node recoloring algorithms.

9 Java Generics
Definition
Generics = Parameterized Types. They allow a class, interface, or method to work with different data types safely — catching type errors at compile time instead of runtime. Introduced in Java 5.
Two Main Objectives of Generics
  • Type Safety — compiler catches type mismatches, no ClassCastException at runtime
  • Code Reusability — write once, use with any type (Integer, String, Double, etc.)
Key Rules
  • Use wrapper classes — can't use primitives (int, char) directly
  • Gen<Integer> and Gen<String> are different types
  • Type parameter names: T (Type), E (Element), K (Key), V (Value)
  • Generics are erased at runtime (type erasure)
Generic Class — 6M Program
class Gen<T> {               // T = type parameter
    T ob;
    Gen(T o) { ob = o; }
    T getob() { return ob; }
    void showType() {
        System.out.println("Type: " + ob.getClass().getName());
    }
}

public class GenDemo {
    public static void main(String[] args) {
        Gen<Integer> iOb = new Gen<>(88);
        iOb.showType();
        int v = iOb.getob(); // No cast needed!
        System.out.println("value: " + v);

        Gen<String> sOb = new Gen<>("Generics");
        sOb.showType();
        System.out.println("value: " + sOb.getob());

        // iOb = sOb;  ← Compile-time ERROR! Type mismatch
    }
}

Restrict which types T can be. <T extends SomeClass> means T must be SomeClass or its subclass. Allows using methods of that class on T.

Generic Type Erasure & Bridge Methods
What is Type Erasure?
Java implemented Generics using Type Erasure to maintain backward compatibility with older pre-Generic Java versions (legacy code). The compiler strips away all generic type parameters during compilation, meaning generic type parameters only exist at compile time. At runtime, the JVM knows nothing about the generic types; all classes are compiled into raw types.
Three Core Compiler Rules of Type Erasure
  • Replacing Type Parameters: The compiler replaces all type parameters in generic types with their bounds if they are bounded (e.g., <T extends Number> becomes Number), or with Object if they are unbounded (e.g., <T> becomes Object).
  • Inserting Explicit Casts: Wherever the generic return type is assigned to a specific reference, the compiler automatically inserts an explicit type cast in the bytecode (e.g., String s = list.get(0) becomes compiled as String s = (String) list.get(0)).
  • Generating Bridge Methods: The compiler generates synthetic helper methods (called Bridge Methods) in subclass implementations to preserve polymorphism in inheritance hierarchies.
Before vs. After Type Erasure (Bytecode level)
1. Generic Code (Written by Developer)
public class Node<T> {
    private T data;
    public Node(T data) { this.data = data; }
    public T getData() { return data; }
}
2. Compiled Code (What the JVM executes)
public class Node {
    private Object data; // Unbounded -> Object
    public Node(Object data) { this.data = data; }
    public Object getData() { return data; }
}
Polymorphic Bridge Methods Explained
Consider this inheritance structure: 
public class MyNode extends Node<Integer> {
    public MyNode(Integer data) { super(data); }
    public void setData(Integer data) { ... } // Overriding!
}
After type erasure, Node's method becomes setData(Object data), but MyNode has a method setData(Integer data).
Since their signatures differ (Object vs Integer), MyNode no longer overrides Node's method at the JVM bytecode level. To fix this and preserve runtime polymorphism, the compiler automatically generates a synthetic Bridge Method in MyNode: 
// Synthetic bridge method generated behind-the-scenes by compiler:
public void setData(Object data) {
    this.setData((Integer) data); // Delegates to type-specific method
}
9b Bounded & Unbounded Wildcards
Definition
A Wildcard Argument (represented by the question mark ?) is used in Generics to represent an unknown type. It is primarily used as parameter types in methods, allowing them to accept arguments of varied generic classifications.
1. Unbounded Wildcard (<?>)

Represents any completely unknown type. Acceptable when a method only performs operations defined in the Object class.

void printList(List<?> list) {
    for (Object obj : list)
        System.out.println(obj);
}
2. Upper-Bounded Wildcard (<? extends T>)

Restricts the unknown type to be **T or any subclass of T**. Ideal for **reading** data from a generic structure safely.

double sum(List<? extends Number> list) {
    double s = 0.0;
    for (Number n : list)
        s += n.doubleValue();
    return s;
}
3. Lower-Bounded Wildcard (<? super T>)

Restricts the unknown type to be **T or any superclass of T**. Ideal for **writing** or adding elements to a generic structure safely.

void addInt(List<? super Integer> list) {
    list.add(10); // Safe to write Integer
}
Bounded Wildcards vs Bounded Types
Feature Bounded Wildcard (<? extends T>) Bounded Type Parameter (<T extends Number>)
Declaration Location Inside **method arguments** only (used as method parameters). At **class/interface declarations** or **generic method signatures**.
Naming Type reference is anonymous (uses ?). Type reference is named (uses T, which can be reused inside the class/method).
Relationship Capabilities Supports both **upper bounds** (extends) and **lower bounds** (super). Only supports **upper bounds** (extends). Lower bounds are not supported.
Best For Providing flexible arguments for method invocation. Designing classes/methods that declare internal fields or return types of type T.
Bounded Wildcard Program — 6 Mark PYQ
import java.util.*;

public class WildcardDemo {
    // Upper-Bounded Wildcard: reads and sums any Number sub-list
    public static double sumOfList(List<? extends Number> list) {
        double sum = 0.0;
        for (Number n : list) {
            sum += n.doubleValue();
        }
        return sum;
    }

    // Lower-Bounded Wildcard: appends integer values safely
    public static void addNumbers(List<? super Integer> list) {
        for (int i = 1; i <= 3; i++) {
            list.add(i);
        }
    }

    public static void main(String[] args) {
        // Testing Upper Bound
        List<Integer> li = Arrays.asList(1, 2, 3);
        System.out.println("Sum of Integers = " + sumOfList(li));

        List<Double> ld = Arrays.asList(1.2, 2.3, 3.5);
        System.out.println("Sum of Doubles = " + sumOfList(ld));

        // Testing Lower Bound
        List<Number> ln = new ArrayList<>();
        addNumbers(ln);
        System.out.println("List after lower-bound addition: " + ln);
    }
}
Output
Sum of Integers = 6.0 Sum of Doubles = 7.0 List after lower-bound addition: [1, 2, 3]

TreeMap with Custom Comparator — Sort by Last Name (From Notes)
import java.util.*;

class TComp implements Comparator<String> {
    public int compare(String a, String b) {
        int i = a.lastIndexOf(' ');
        int j = b.lastIndexOf(' ');
        int k = a.substring(i).compareTo(b.substring(j));
        return (k == 0) ? a.compareTo(b) : k;
    }
}

class TreeMapDemo2 {
    public static void main(String[] args) {
        TreeMap<String, Double> tm = new TreeMap<>(new TComp());
        tm.put("John Doe", 3434.34);
        tm.put("Tom Smith", 123.22);
        tm.put("Jane Baker", 1378.00);
        tm.put("Tod Hall", 99.22);
        tm.put("Ralph Smith", -19.08);

        for (Map.Entry<String, Double> me : tm.entrySet())
            System.out.println(me.getKey() + ": " + me.getValue());
    }
}
Output
Jane Baker: 1378.0 John Doe: 3434.34 Tod Hall: 99.22 Ralph Smith: -19.08 Tom Smith: 123.22
Note: Sorted by last name (Baker, Doe, Hall, Smith, Smith). For same last names, full name comparison used.
Generics — max() Generic Method with Comparable Bound
public class Util {
    public static <T extends Comparable<T>> T max(T a, T b, T c) {
        T m = a;
        if (b.compareTo(m) > 0) m = b;
        if (c.compareTo(m) > 0) m = c;
        return m;
    }
    public static void main(String[] args) {
        System.out.println(max(3, 7, 5));
        System.out.println(max("apple", "banana", "kiwi"));
    }
}
Output
7 kiwi

class Box<T> {
    private T value;
    Box(T value) { this.value = value; }
    T getValue() { return value; }
}

public class Main {

        Box<Integer> i = new Box<>(42);
        Box<String>  s = new Box<>("Hello");

    }

13 Viva Questions & Quick Answers
Q: What is the difference between Iterator and ListIterator?
Iterator can traverse only forward; ListIterator (for List only) can traverse both forward and backward, and also add/set elements during traversal.
Q: Why can't we use primitive types with Generics?
Generics require reference types. Primitives (int, char) are not objects. Use wrapper classes: Integer, Character, Double, etc. Java does autoboxing automatically.
Q: What is type erasure in Generics?
At runtime, all generic type information is removed by the compiler. Gen<Integer> and Gen<String> both become Gen at runtime. This is called type erasure — generics are a compile-time feature only.
Q: What happens if you try to add null to a TreeSet?
It throws NullPointerException because TreeSet uses compareTo() to sort, and null cannot be compared.
Q: What is the difference between Comparable and Comparator?
Comparable defines natural ordering inside the class (compareTo method). Comparator defines custom ordering outside the class (compare method). Comparable = one sort order; Comparator = multiple sort orders possible.
Q: Can we sort a HashSet? How?
HashSet itself doesn't maintain order. To sort, either: (1) use TreeSet instead, or (2) copy HashSet to ArrayList and use Collections.sort().
Q: What is the difference between Collection and Collections?
Collection (with lowercase 'c' after) is an interface — root of List, Set, Queue. Collections (with 's') is a utility class with static methods like sort(), reverse(), shuffle(), min(), max().
Q: What is a bounded wildcard in generics?
<T extends Number> is an upper-bounded type — T can be Number or any of its subclasses. <? super Integer> is lower-bounded — anything that is a superclass of Integer.
Q: Why does Map not extend Collection?
Because Map stores key-value pairs, not single elements. The Collection interface is designed for individual elements. Map has a completely different API (put, get, entrySet, etc.).
Q: What is ConcurrentModificationException?
Thrown when you modify a collection (e.g., remove elements using list.remove()) while iterating over it with a for-each loop. Solution: use iterator.remove() instead.
Q: What are the advantages of using Spliterator over Iterator?
Spliterator supports parallel processing (trySplit() method), can estimate size, and is designed for Java 8 Streams. Iterator only supports sequential, single-threaded traversal.
Q: What is a generic interface?
An interface that accepts a type parameter: interface MyInterface<T> { void show(T data); }. A class implementing it specifies the type: class A implements MyInterface<String>. This allows the interface to work with multiple types while maintaining type safety.

Return Value Tricks
  • compareTo / compare: neg → <, 0 → =, pos → >
  • Reverse sort: return b.compareTo(a)
  • Ascending int sort: a - b
  • Descending int sort: b - a
